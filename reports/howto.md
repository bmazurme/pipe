# HOWTO: модуль Subscription — от задачи GitLab до посылки в bridge и обратно

Практическое руководство по разделу **Подписка**: как отправить задачу
GitLab в bridge (с ревью текста перед отправкой), как создать посылку без
реальной задачи в GitLab, как удалить запись из пайплайна, и как
пользоваться отдельной страницей **Purge**. Для приёма посылок на другой
машине через `sync-cli agent-runner` см. `sync/howto.md` — это документ про
противоположный конец того же потока.

## Разовая настройка

1. **Настройки → Подключение к GitLab** — URL и токен доступа. Без этого
   список открытых задач не загрузится.
2. **Настройки → Отслеживаемые репозитории** — добавьте локальный путь к
   репозиторию для каждого `gitlabProjectId`, с которым будете работать
   через Subscription. Без этого init/push для задачи этого проекта
   откажет с ошибкой «Этот проект не отслеживается».
3. **Настройки → Словарь подстановки** — пары ключ/значение
   (реальное значение → плейсхолдер), которые push/pull подставляют в код и
   текст задачи. Пустой словарь означает, что текст уходит без изменений —
   `Purge` (см. ниже) предупредит об этом.
4. **Настройки → Шифрование посылок** — включите и сгенерируйте пару ключей,
   если посылки должны быть зашифрованы на bridge. Публичный ключ шифрует
   исходящую посылку, приватный — расшифровывает входящую; экспортируйте оба
   («Экспорт»), если посылку потом нужно будет забрать через `sync-cli`
   (см. `sync/howto.md`, раздел про `.enc`-парцели).
5. **Настройки → Интеграция с bridge** — Bridge API URL и ключ (или
   refresh-токен) для доступа к хранилищу.

## Обычный путь: реальная задача GitLab

1. Откройте **Подписка** — список открытых задач, назначенных вам в GitLab.
2. Кликните по задаче → **Инициализировать** (шаг `init`): создаёт ветку в
   локальном репозитории по маске имя-дата-номер задачи.
3. **Отправить** (шаг `push`): вместо немедленной отправки открывается форма
   предпросмотра — заголовок и описание задачи, уже пропущенные через
   словарь (`ключ → значение`), как это было бы отправлено. Правьте прямо в
   полях формы. Если после подстановки словаря в тексте всё ещё
   обнаруживаются похожие на секреты значения (email, IP, токен), под
   формой появится предупреждение с кнопкой **«В словарь»** у каждой
   находки — добавляет пару в словарь одним кликом со сгенерированным
   значением, без выхода из формы.
4. **Подтвердить и отправить**: то, что видно в полях на этот момент, и
   уходит в архив — ни разу больше не запрашивается «живой» текст задачи из
   GitLab. Кодовая база отслеживаемого репозитория (тоже пропущенная через
   словарь) упаковывается в тот же архив и отправляется в bridge.
5. На другой машине заберите посылку через `sync-cli agent-runner --review`
   (`sync/howto.md`) или через `pull` в этом же разделе Subscription, если
   работаете локально в той же кодовой базе.
6. После pull, при необходимости, **Отправить повторно** — та же форма
   предпросмотра, пайплайн возвращается на шаг `pull`.
7. **Опубликовать** (шаг `publish`): необязательный шаблон комментария и
   оценка времени, публикуется в GitLab-задачу.

## Посылка без задачи в GitLab

Иногда нужно прогнать через тот же pipeline произвольный текст — не
привязанный к реальной задаче GitLab (черновик, внутренняя заметка,
эксперимент).

1. **Подписка → Добавить вручную**: выберите отслеживаемый репозиторий,
   впишите заголовок и описание. Создаётся запись с шагом `init` (ветка уже
   создана) — без обращения к GitLab.
2. Дальше — тот же путь: **Отправить** открывает ту же форму предпросмотра
   (заполненную сохранённым текстом вместо запроса к GitLab), push/pull
   работают идентично реальной задаче.
3. **Опубликовать** для такой записи не пытается что-либо комментировать в
   GitLab (комментировать нечего) — только отмечает локальный шаг как
   завершённый, для единообразия с реальными задачами.

Такие записи помечены бейджем «Вручную» в списке и живут только в
локальном состоянии этой машины (`subscription-state.json`) — в GitLab их
нет и не будет.

## Удаление записи

Кнопка-корзина у каждой строки в списке. Для реальной задачи GitLab это
сбрасывает только локальный прогресс (init/push/pull/publish) — сама задача
остаётся в GitLab и снова появится в списке с шага «Не начато». Для
вручную созданной посылки состояние — единственное место, где она вообще
существует, так что удаление стирает её полностью и без возможности
восстановления.

## Purge: подстановка словаря без привязки к задаче

Отдельная страница **Purge** в сайдбаре — reports-версия того же
Purge-инструмента, что есть в bridge, на том же словаре, который push/pull
используют для задач. Полезна, когда нужно вручную анонимизировать/
де-анонимизировать произвольный текст (скопировать в чат с агентом, вставить
в тикет и т.п.), не создавая для этого отдельную посылку.

1. Вставьте текст, выберите направление (`Ключ → значение` — анонимизация,
   `Значение → ключ` — обратная подстановка).
2. **Применить** — результат заменяет текст в том же поле, показывает
   количество замен.
3. При направлении «Ключ → значение» результат дополнительно проверяется
   эвристикой на характерные утечки (email, IP, похожие на токены строки) —
   так же, как это происходит при push задачи. Находки можно сразу добавить
   в словарь через кнопку **«В словарь»**.
4. **Копировать** — копирует текст в буфер обмена и очищает поле (только
   после успешного копирования, чтобы неудачная попытка не потеряла текст).

Подстановка выполняется на сервере reports (а не в браузере, как в bridge)
— клиент reports не тянет зависимость на `@pipe/protocol`. Поскольку сервер
reports работает только локально на машине пользователя, это не создаёт
дополнительного риска приватности.
