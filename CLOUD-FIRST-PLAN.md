## 3. Целевая схема

```
                  reg.ru DNS (ns1/ns2) — A/TXT меняет только `infra/dns` (REG.API)
                         bridge.ntlstl.dev, api.bridge.ntlstl.dev  TTL 120
                                   │
            ┌──────────────────────┴───────────────────────┐
            ▼ site=vm (норма)                              ▼ site=pi (после отказа VM)
 СЛОЙ 1: VM 89.169.132.49                       СЛОЙ 2: дом, 89.207.218.46 → 192.168.50.10
 ┌───────────────────────────────┐   WireGuard  ┌──────────────────────────────────┐
 │ nginx/Caddy (TLS)             │◄────────────►│ red: Postgres hot standby        │
 │ bridge: backend, frontend     │  10.77.0.0/24│ white: стек bridge (backend = 0),│
 │ bridge-pg (Postgres 16, ПЕРВИЧ)│  потоковая   │        Garage, бэкапы, NAS       │
 │ worker (ограниченный)         │  репликация  │ blue: сторож (наблюдатель №1)    │
 │ vpn-client (Telegram-прокси)  │  VM → red    │ red/blue/green: воркеры          │
 │ notes, places, galkina, ntlstl│              │ 3-я копия бэкапов (NAS)          │
 │ агент мониторинга → bridge    │              └──────────────────────────────────┘
 └───────────────────────────────┘
 наблюдатель №2: GitHub (external-probe), №3: сторож на VM-независимой точке (см. §5.4)
```

Принципы:

1. **Слой живёт без соседа.** VM не зависит от Pi (ни образы, ни файлы, ни DNS); Pi не зависит от VM. Связь между ними — только репликация/бэкапы и наблюдение.
2. **Лидер один.** Backend bridge нельзя запускать в двух экземплярах (планировщики Improve, long-polling Telegram → HTTP 409, двойные уведомления) [факт, ha-dr-plan §8.4].
   Активен слой, на котором Postgres на запись **и** чей `site` записан в эпохе (см. §5.3).
3. **Реплика — не бэкап.** `DROP TABLE` реплицируется мгновенно; поэтому отдельные дампы с проверкой восстановления остаются (§6).
4. **Pull-модель.** Резервные копии забирает Pi/NAS сами; взлом VM не даёт доступа к копиям (как в `infra/backup`).
5. **Воркеры — без состояния.** Они опрашивают bridge по имени `api.bridge.ntlstl.dev` и работают с активным слоем после смены DNS (с задержкой ≤ TTL) [факт, ha-dr-plan §8.4].

## 5. Механизмы

### 5.1. Репликация и бэкапы bridge
VM — первичный `bridge-pg`; red — hot standby через WireGuard (`10.77.0.0/24`, как в ha-dr-plan §4.6; VM — публичная точка, дом подключается исходящим соединением; UDP-порт
WireGuard на VM открыт только с 89.207.218.46). Слот репликации `standby_red`, проверка лага каждые 5 минут (`infra/standby/check.sh`, расширить). Алерт: лаг ≥ 60 с — замечание,
≥ 10 минут — проблема, ≥ 15 — автоматический переход запрещён (RPO 15 минут, решение 2026-10-30).

### 5.2. Переключение трафика — что и в каком порядке делает `promote`
1. Проверка: VM не отвечает **по двум независимым путям** (см. §5.4); лаг реплики известен и меньше порога.
2. Попытка «забора» VM: SSH `docker service scale bridge_backend=0` → при недоступности — остановка VM через API Yandex Cloud (**если дадите сервисный аккаунт**; необязательно).
3. `pg_ctl promote` на red; в таблице `site_leader` эпоха `N+1`, `site=pi`.
4. Старт backend в стеке Pi; локальная проверка `/api/v1/health/leader`.
5. REG.API: A-записи `bridge`/`api.bridge` → 89.207.218.46, TXT `_leader.ntlstl.dev` = `epoch=N+1;site=pi;ts=…`.
6. Caddy на Pi выпускает сертификат (HTTP-01, 1–2 мин, как в текущем failover).
7. Сообщение в Telegram и issue-запись; в дашборде плитка показывает «лидер: Pi».

### 5.3. Эпоха и самозабор (защита от split-brain) — **новый код в bridge**
- Таблица `site_leader(epoch, site, updated_at)`; `SITE_ID` в окружении backend (`vm` | `pi`).
- Backend раз в 15 с читает **авторитативно** (`dig @ns1.reg.ru`, без кэша резолверов) TXT `_leader.ntlstl.dev`. Если эпоха в TXT **больше своей** и `site` ≠ свой — backend **самоограничивается**:
  `/api/v1/health/leader` отвечает 503, планировщики Improve и Telegram-опрос останавливаются, мутирующие запросы получают 503.
  Не получилось прочитать DNS — **не** считаем это отказом (иначе сбой DNS положит работающий слой); состояние не меняется.
- При загрузке VM (после падения) systemd-юнит `pipe-leader-gate` читает тот же TXT **до** запуска стека: если лидер уже Pi — стек не стартует, VM ждёт процедуры failback.
- Объём работ [оценка]: 2–3 дня + тесты (backend, миграция, OpenAPI по шагам из CLAUDE.md).
- Известный остаток риска: VM жива, но оторвана от DNS и от наших проверок — клиенты со старым кэшем DNS могут писать на неё до TTL (120 с). Этим риском мы платим за недопустимость «упавшая сеть = автопереход».

### 5.4. Наблюдатели
Переход разрешён, только если «VM не отвечает» подтверждают **минимум два из трёх**:
1. **blue** (дом) — `primary-watch` переписать «site-aware»: проверяет публичный `https://api.bridge.ntlstl.dev/api/v1/health/leader` и WireGuard-адрес VM;
2. **GitHub** — `external-probe.yml` (каждые 10 мин, issue `outage`): расширить на notes/places/ntlstl.dev и на заголовок `X-Pipe-Site` (кто отвечает);
3. **внешняя точка вне VM и вне дома** — нужен третий независимый наблюдатель [вопрос Q7]; без него — два (blue + GitHub), порог 3 минуты, ступень A/B.
Если у самого blue нет связи с интернетом (он сам отрезан), он ничего не решает и не голосует [факт: так уже сделан `primary-watch`].

### 5.5. DNS через REG.API (`infra/dns/`)
- Скрипты: `regru.sh` (обёртка над REG.API 2.0: список записей зоны, добавление/удаление A и TXT, чтение авторитативным запросом), `flip.sh <vm|pi>`, `acme-hook.sh` (для certbot DNS-01), тесты с поддельным API.
- Из сторонних клиентов видно, что REG.API имеет метод `zone/update_records` (пакет действий над записями), а смена NS — `domain/update_nss`; **точные имена действий и параметры берём с официальной страницы reg.ru/support/help/api2 до реализации** — поиск вернул мне только сторонние обёртки [не проверено].
- Доступ к API у reg.ru обычно привязан к IP и/или паролю API [не проверено]: пускаем только с адреса дома 89.207.218.46 (статичный, [факт]); флипер живёт на Pi.
- Ключ REG.API — **самый чувствительный новый секрет** (кто им владеет, тот управляет доменом): хранится зашифрованным (age), в окружении только у флипера, не в GitHub Secrets, включён 2FA на аккаунте reg.ru и «защита от переноса» домена.
- TTL у `bridge`/`api.bridge` ставим 120 с заранее (за ≥ 10 минут до первого флипа: текущий TTL 600).

### 5.6. «Переключение NS» — что это на самом деле
Смена **набора серверов имён** (`domain/update_nss`) идёт через регистратор и родительскую зону `.dev`; время вступления определяет кэш делегации, которым мы не управляем
[не проверено: измерить `dig +trace`], и работает только если новая сторона **уже хранит копию зоны**. Для переключения слоёв это слишком медленно и хрупко, поэтому:
- переключение VM↔Pi делаем **сменой A-записей** (§5.5) — секунды/минуты;
- «отказ самого DNS reg.ru» закрываем отдельной ступенью (Этап 9b): **второй DNS-провайдер** с копией зоны, оба набора NS публикуются у регистратора заранее, `flip.sh` пишет в обе зоны. Тогда экстренная смена NS не нужна; скрипт `update_nss` остаётся аварийной кнопкой.
- Провайдер для второй зоны — **не Yandex Cloud DNS** (тот же аккаунт и домен отказа, что слой 1). Выбор — вопрос Q4.

## 7. Ресурсы VM — проверка и решение

Факт: 1963 МБ всего, `available` 606 МБ при работающем старом bridge-стеке, swap 0, диск свободно 9,6 ГБ. Оценки (**[оценка]**, замерить до шага):

| Нагрузка | Оценка памяти | Комментарий |
|---|---|---|

## 8. Мониторинг VM и её сервисов в дашборде

**Что показывает плитка «Облако»** (по образцу NAS/ИБП/Роутер): вердикт и причины; лидер (`vm`/`pi`) и эпоха; доступность по каждому публичному адресу (bridge, api.bridge, notes, places, ntlstl.dev) с кодом и временем ответа;

Пороги (предложение, правятся при реализации): доступной памяти < 15 % или < 250 МБ — проблема, < 25 % — замечание; swap > 50 % — замечание; диск ≥ 90 % проблема, ≥ 80 % замечание; критичный сервис не `running/desired` — проблема;
нет отчётов 5 минут — проблема; лаг реплики — как §5.1.

**Реализация (код):**
- `infra/cloudagent/` — агент (bash+python3, как `infra/boardagent`; юнит и таймер 1 минута; свой ключ «только для плат»); список сервисов и их критичность — в `/etc/pipe-cloudagent.env`.

- **Агент шлёт отчёт на публичный `api.bridge.ntlstl.dev`**, а не на localhost: после failover вернувшаяся VM окажется «устаревшей» в дашборде нового лидера, а не пишет в свою старую БД.

### Этап 8 — Переключение трафика на VM, white → резерв (0,5 дня + окно ≈ 30 мин)

2. Запуск backend на VM (`LEADER_ENFORCE=on`), проверка `--resolve`, `health`, вход, задача.
3. DNS: `bridge`/`api.bridge` → 89.169.132.49; TXT `_leader` = `epoch=1;site=vm`. Контроль: `dig @ns1.reg.ru`, внешний пробник, плитка «Облако».

### 12.1. Команды инвентаризации на VM (только чтение; значения секретов не печатать)
```bash
# версии, ресурсы
docker version --format '{{.Server.Version}}'; docker info --format '{{.Swarm.LocalNodeState}}'
free -m; df -h /; docker system df; docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'
ps aux --sort=-rss | head -15
# сеть и открытые порты (какие слушают на 0.0.0.0)

docker service inspect bridge_backend --format '{{json .Spec.TaskTemplate.ContainerSpec.Env}}' | tr ',' '\n' | sed 's/=.*/=<скрыто>/'
# Postgres: версия, базы, размеры, роли
docker exec postgres psql -U postgres -c "select version()" -c "select datname, pg_size_pretty(pg_database_size(datname)) from pg_database" -c "\du"
docker inspect postgres --format '{{.Config.Image}} {{json .Mounts}}'
# nginx / сертификаты
ls /etc/nginx/sites-enabled; sudo certbot certificates 2>/dev/null | grep -E 'Name|Expiry'
# minio, grafana, prometheus: что хранят
docker inspect minio --format '{{json .Mounts}}'; docker exec minio ls /data 2>/dev/null | head
# SSH
sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin|pubkeyauthentication'
# последняя перезагрузка и её причина
last -x reboot | head -3; journalctl --list-boots | tail -3
```
