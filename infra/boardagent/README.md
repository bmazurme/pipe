# Агент плат: обновление скриптов по кнопке

Платы получают скрипты вручную (`scp` + `install.sh`), и влитое в `main` исправление может неделями не доезжать (так было с
`uploads-pull.sh` на red). `infra/scriptcheck` об этом предупреждает, а этот агент позволяет **разрешить обновление кнопкой** — в
Telegram или на странице «Платы» в bridge, — не заходя на плату.

```
плата ──(раз в час: отчёт)──► bridge ──► сообщение в Telegram с кнопкой «⬆️ Обновить ubuntu-red» / страница «Платы»
плата ◄──(раз в минуту: есть ли разрешение?)── bridge ◄── вы нажали кнопку
плата ставит скрипты ──► результат в bridge ──► сообщение в Telegram
```

Плата сама опрашивает bridge (как worker), bridge к платам не подключается и ключей от них не хранит.

## Что может разрешение, а что нет

Решение принимает **агент на плате**, а не bridge: ошибочный или взломанный bridge не должен получить возможность поставить код на плату.

- Только скрипты из **собственного списка агента** (`manifest.txt`, копируется вручную вместе с агентом) и только по пути, который
  даёт этот список. Список совпадает с тем, что сравнивает `check-scripts.sh` (тест это проверяет).
- Только скрипты, **уже установленные** на этой плате: новых файлов агент не создаёт.
- Только из коммита, который **есть в `main`** (compare на GitHub отвечает «behind» или «identical»); файлы берутся с GitHub по этому коммиту.
- **Агент обновляет и себя** (только `board-agent.sh` и `manifest.txt`; `install.sh`, `rollback.sh` и юниты — вручную). Это самое опасное
  обновление, поэтому оно идёт в несколько ступеней: (1) новая пара (скрипт + список) кладётся во временный каталог и **проходит
  `board-agent.sh selftest`** — синтаксис, список, ответ bridge, `check-scripts.sh --json`; не прошла — ничего не заменяется, причина в
  Telegram; (2) старая пара сохраняется в `/var/lib/pipe-boardagent/agent-prev/`; (3) файлы заменяются атомарно, и остаётся метка
  `agent-update.pending`; (4) метку снимает первый же запуск нового агента, получивший ответ bridge («agent update verified»); (5) если
  новый агент **упал** на первом запуске, systemd (`OnFailure` у `pipe-boardagent-apply.service`) запускает `rollback.sh`: он возвращает
  старую пару и сообщает в Telegram. `rollback.sh` крошечный и сам не обновляется, поэтому сломанный агент не ломает то, что его
  восстанавливает. Откат можно сделать и руками: `sudo /usr/local/lib/pipe-boardagent/rollback.sh`.
- Каждый shell-скрипт проходит `bash -n` до замены; старый файл сохраняется в `/var/lib/pipe-boardagent/backup/<id>/`; при любой
  ошибке установки или проверки все уже заменённые файлы возвращаются на место.
- Разрешение действует час: если плата выключена, оно истекает, а не применяется неожиданно потом. Кнопка из старого сообщения
  («main с тех пор сдвинулся») отклоняется: применяется тот коммит, который вы видели.
- Обновляются **только файлы**. Если изменение требует переустановки unit'ов или таймеров (то есть `install.sh` каталога), этого агент
  не делает — смотрите README соответствующего каталога.

## Установка (на каждой плате, вручную)

```bash
scp -r infra/boardagent pi@HOST:~/ && ssh -t pi@HOST 'sudo bash ~/boardagent/install.sh'
ssh -t pi@HOST 'sudo nano /etc/pipe-boardagent.env'     # BRIDGE_API_KEY = API-ключ ВЛАДЕЛЬЦА только для плат (bridge: Профиль → API-ключи → «только для плат»; полный ключ не нужен)
ssh pi@HOST 'sudo systemctl start pipe-boardagent-report.service && sudo journalctl -u pipe-boardagent-report.service -n 5 --no-pager'
```

Нужен установленный `infra/scriptcheck` (агент спрашивает у него, что устарело). Ключ должен принадлежать владельцу: чужой ключ
bridge отклонит. Установщик отключает `ALERT_CMD` в `/etc/pipe-scriptcheck.env` (оставляя строку комментарием): теперь сообщение шлёт
bridge, с кнопкой, и второе без кнопки ни к чему.

После первого отчёта плата появляется на странице «Платы». Удалить: `sudo bash ~/boardagent/install.sh --remove`.

## Проверка и разбор

```bash
sudo systemctl list-timers 'pipe-boardagent*'
sudo journalctl -u pipe-boardagent-apply.service -u pipe-boardagent-report.service --since '1 hour ago' --no-pager
sudo /usr/local/lib/pipe-scriptcheck/check-scripts.sh --json     # что агент отправит в отчёте
```

| Симптом | Причина |
|---|---|
| «BRIDGE_API_KEY is not set» | ключ не вписан в `/etc/pipe-boardagent.env` |
| отчёт не принят (`401`/`403`) | ключ не владельца или отозван |
| плата не появляется на странице | таймер отчёта ещё не сработал: `sudo systemctl start pipe-boardagent-report.service` |
| «commit … is not on main» | коммит не влит в `main` (или ветка сдвинулась в обратную сторону): отказ намеренный |
| «refused: … is not in this board's manifest» | устарел список агента: обновите агент вручную (`install.sh`) |
| «does not pass bash -n» | в коммите синтаксическая ошибка в скрипте; плата ничего не заменила |

## Первая установка версии с самообновлением — вручную
Более старые агенты обновить себя не могут (у них нет ни `selftest`, ни отката), поэтому **эту** версию на каждую плату нужно один раз
поставить вручную тем же `scp` + `install.sh` (он добавит `rollback.sh` и юнит отката). Дальше агент обновляется кнопкой, как остальные
скрипты. Требование к будущим версиям: `selftest` должен продолжать работать — им текущий агент проверяет следующий.

## Показатели плат и надёжная связь с bridge

Тот же запуск `apply` (раз в минуту) каждые `METRICS_EVERY_SEC` секунд (по умолчанию 120) присылает на `POST /api/v1/boards/agent/metrics` показатели платы:
температуру процессора, младшие 4 бита `vcgencmd get_throttled` («прямо сейчас»: просадка питания, ограничение частоты, троттлинг, мягкий предел температуры),
обороты кулера, температуру NVMe (`/sys/class/nvme/nvme0/hwmon*/temp1_input`, `nvme-cli` не нужен), нагрузку, свободную память, заполнение диска, аптайм.
Показатель, который снять не удалось, опускается, а не выдумывается. `METRICS_EVERY_SEC=0` выключает. Попытка, а не успех, ограничивается по частоте: недоступный
bridge не получает по два таймаута в минуту. Метрики никогда не задерживают решение об обновлении.

Со вторым значением по умолчанию агент ходит к bridge **сначала по адресу стека внутри сети** (`curl --resolve api.bridge.ntlstl.dev:443:192.168.50.10`), чтобы запрос
не выходил через роутер и провайдера и не зависел от них, а если по этому адресу не достучаться совсем (curl 6/7/28/35/52/56) — повторяет обычным путём. Ответ 4xx/5xx
повтором не считается: запрос не уходит дважды. Переопределить: `BRIDGE_RESOLVE=host:port:ip` в `/etc/pipe-boardagent.env`; `BRIDGE_RESOLVE=` (пусто) — не закреплять.
Версия агента 2; на страницу «Платы» она выходит в «агент 2» после первого отчёта.
