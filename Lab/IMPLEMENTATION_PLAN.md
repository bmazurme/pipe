# Lab — оценка проекта и план реализации

Это MVP для шага 5.1 из анализа интеграции CAD в `pipe` (идея → характеристики →
расчёт → чертёж/модель → производство → испытания → оптимизация по цене): самостоятельный
Python-проект, без worker/bridge, чтобы до вложений в инфраструктуру проверить сам
расчётный/геометрический подход на реальном железе RC-катера. Запущен и проверен
end-to-end на двух доменах (катер, самолёт) — результаты ниже.

## 1. Что подтверждено реальным запуском

**Инструментарий работает.** `build123d` (OCCT-биндинг) ставится и работает на
macOS/arm64/Python 3.14 через `cadquery-ocp-novtk`/`cadquery-ocp-proxy` — колёса под этот
не самый типичный таргет (очень свежий Python) нашлись и отработали без доработок.
Проверено: лофт по сечениям, `volume`/`area`/`bounding_box`, разрез тела плоскостью
(`split`, нужен для ватерлинии), экспорт в STEP (прошёл как валидный AP214) и STL.

**Архитектурная модульность подтверждена, а не просто задекларирована.** После того как
`boat` был написан и работал, `aircraft` (другой класс изделия — крыло вместо корпуса,
другая физика — wing loading вместо гидростатики) был добавлен без единого изменения в
`lab/core/`: только `lab/domains/aircraft/{__init__,geometry,calculators}.py` + строка в
`lab/domains/__init__.py` + `project.yaml`. Это и была главная цель уточнения "заложить
модульность в архитектуру" — проверено кодом, не только спроектировано на бумаге.

**Расчёт на реальном прогоне `rc-boat-demo`** (600×160×90мм, PLA, 180 Вт):

| Показатель | Значение |
|---|---|
| Масса корпуса (оболочка 2.4мм) | 0.786 кг |
| Масса всего изделия | 1.091 кг |
| Ватерлиния / запас борта | 21.1 мм / 68.9 мм (погружено 23%) |
| Расчётная скорость (формула Крауча) | 45.4 км/ч при цели 35 |
| Время печати (константная модель) | 35.7 ч |
| Итоговая стоимость | 6344 ₽ при бюджете 3000 ₽ |

## 2. Что эти цифры сами по себе уже говорят — находки, а не только механика

Это именно то, ради чего строился MVP — не просто "скрипт запустился", а "подход
вскрывает реальные проектные решения ещё до печати":

- **Дважды превышен бюджет** — в основном из-за станко-часов печати (1429 ₽ из 1415+1429
  материал+печать), не материала. Это прямое указание: либо снижать время печати
  (толщина стенки, ориентация, разделение на части), либо запрос «бюджет 3000 ₽» для
  такого размера корпуса в PLA нереалистичен — то и есть "оптимизация по цене" в
  действии, без единого физического прототипа.
- **Расчётная скорость выше цели на треть** — похоже, что 180 Вт для этого корпуса
  избыточны: можно поставить более дешёвый/лёгкий мотор и уменьшить и стоимость, и массу
  (которая напрямую снижает требуемое водоизмещение и материал корпуса).
- **35.7 часа печати — подозрительно много**, и это осознанно самый слабый элемент
  MVP: константа `18 см³/ч` (`lab/core/printing.py`) не учитывает, что большая простая
  оболочка печатается куда быстрее при реалистичных настройках слайсера. Это следующий
  по приоритету пункт плана (п.3), а не повод не доверять остальным цифрам — гидростатика
  и масса считаются из настоящего объёма/площади тела, а не из этой константы.

Иными словами: уже на этом MVP видно, что связка «геометрия → масса → стоимость →
простая физика» действительно даёт основание для инженерного решения, а не только
красивые STEP-файлы. Это и есть ответ на "оценку проекта" — подход работоспособен,
стоит продолжать.

## 3. Что заведомо не точно (сделано по плану, не по недосмотру)

| Упрощение | Где | Почему допустимо для MVP | Что заменить дальше |
|---|---|---|---|
| Скорость — формула Крауча, не Savitsky | `domains/boat/calculators.py` | Даёт порядок величины за одну формулу, без итеративного решения по углу трима | Savitsky (итеративный) или калибровка по реальным заездам |
| Время/стоимость печати — константная производительность | `core/printing.py` | Не требует установленного слайсера для MVP | Реальный вызов PrusaSlicer/аналога CLI по STL |
| Крыло — плоская пластина, не профиль | `domains/aircraft/geometry.py` | Доказывает архитектуру, не несёт аэродинамического смысла | Лофт по сплайнам NACA/Clark-Y |
| Нет FEM/прочности | — | Не нужно для первой оценки подхода | gmsh + CalculiX, см. анализ интеграции (предыдущее сообщение) |
| Каталог материалов — ориентировочные ₽/кг | `core/materials.py` | Достаточно для сравнения итераций друг с другом | Реальный прайс поставщика / калибровка по чекам |

## 4. План реализации дальше (фазы, без изменений в п.1-2 этого документа)

Нумерация продолжает фазы из предыдущего анализа интеграции в экосистему `pipe`; этот
MVP закрывает фазу 1.

**Фаза 2 — довести расчётную точность, не трогая архитектуру**
- Реальный слайсер CLI вместо константы (`core/printing.py` — единственный файл меняется).
- Savitsky вместо Крауча (`domains/boat/calculators.py` — только этот домен).
- Профиль крыла вместо пластины (`domains/aircraft/geometry.py` — только этот домен).
- Калибровочные параметры (анизотропная прочность филамента и т.п.) — новые поля в
  `core/materials.py`, заполняются из будущих результатов испытаний (фаза 4).

**Фаза 3 — FEM**: gmsh (сетка) + CalculiX (решатель) как новый generic-хелпер в
`core/`, аналогичный `core/printing.py` — принимает `PartSpec` + граничные условия,
которые домен формулирует сам (домен знает, где у корпуса опора/нагрузка, core — только
запускает решатель и возвращает числа).

**Фаза 4 — модуль bridge «Hardware/Lab»**: сущности `DesignRevision`/`Metric`
(`predicted`/`measured`)/`BomLine`/вложения, как описано в предыдущем анализе
интеграции. `results.json` этого MVP — почти готовый формат для записи `predicted`-метрик
туда: ключи `calculations.*`, `total_cost_rub`, `total_mass_kg` переносятся как есть.

**Фаза 5 — CAD-worker**: отдельный Docker-образ с `build123d`+слайсером+gmsh/CalculiX,
тег «способности» у worker'а, `agentRunner`/Improve дают задачу правки `project.yaml`/
`domains/*` и прогоняют `lab run` внутри — тот же CLI, что и в этом MVP, без переписывания.

**Фаза 6** — направление в Improve "оптимизация по цене/массе" поверх накопленной
истории ревизий — как и было описано ранее.
