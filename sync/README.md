# sync-cli

Синхронизирует дерево исходников JS/TS-проекта между двумя компьютерами
через уже существующий модуль хранения файлов [`bridge`](https://github.com/)
(`/api/v1/storage`) — без каких-либо изменений в самом bridge.

## Идея

- Словарь — пары `{ key: реальное значение, value: плейсхолдер }`, как в
  Purge на bridge (там то же самое: ключ вводится вручную как реальный
  термин, значение — автоподставленный токен той же длины).
- `push` проходит по файлам проекта, заменяет `ключ -> значение`
  (реальное на плейсхолдер, обезличивает), пакует в zip и грузит в bridge.
- `pull` скачивает последний запушенный zip, заменяет `значение -> ключ`
  (плейсхолдер обратно на реальное) и раскладывает файлы поверх рабочей копии.
- На bridge всегда лежит только "обезличенный" код с плейсхолдерами.
- Если словарь пустой (`[]`) — замены не делаются вообще, ни в push, ни в
  pull, содержимое передаётся как есть.
- Файл словаря (`dictionaries/*.json`) не синхронизируется через sync-cli —
  он держится локально на каждой машине намеренно (чтобы реальные значения
  не гуляли лишний раз). Сам словарь при этом хранится централизованно в
  Purge на bridge (по аккаунту, не по машине) — так что на каждой машине
  достаточно зайти в Purge → Словарь → «Экспорт» и положить получившийся
  файл на нужный путь; т.к. это один и тот же аккаунт, содержимое будет
  идентичным везде.

Транспорт — `POST/GET /api/v1/storage`, `GET /api/v1/storage/:id/download`.
Скачивание там **удаляет файл на бридже** — это специально устроенная
семантика "почтового ящика на одного получателя", которая идеально подходит
паре компьютеров: то, что запушено с машины A, прочитает только машина B.

## Установка

```bash
npm install
npm run build
```

## Настройка

1. Скопируйте `sync.config.example.json` в `sync.config.json` и укажите
   реальные пути к отслеживаемым папкам-проектам на этой машине:

   ```bash
   cp sync.config.example.json sync.config.json
   ```

   Или через CLI:

   ```bash
   node dist/cli.js add bridge /Users/you/GitHub/bridge dictionaries/bridge.json
   node dist/cli.js add reports /Users/you/GitHub/reports dictionaries/reports.json
   node dist/cli.js list
   ```

2. Заполните локальный словарь для каждого проекта, например
   `dictionaries/bridge.json`. Проще всего — открыть в bridge страницу
   **Purge** (вкладка «Словарь») и нажать «Экспорт»: файл
   `purge-dictionary-YYYY-MM-DD.json` можно положить как есть под именем
   `dictionaries/bridge.json`, формат тот же (`[{ "key": ..., "value": ... }]`).
   Можно и вручную — sync-cli также понимает плоский объект:

   ```json
   [{ "key": "prod-db.internal.example.com", "value": "{{DB_HOST}}" }]
   ```

   `key` — реальное значение (то, что есть в коде на этой машине), `value` —
   плейсхолдер, который увидит bridge и вторая машина. **Повторите этот шаг
   на каждой машине** — файл не синхронизируется автоматически (он
   намеренно локальный), но т.к. Purge хранит словарь по аккаунту, экспорт
   на любой машине с тем же логином даст один и тот же файл. Замена
   учитывает границы слов (как и сам Purge), так что короткий ключ вроде
   `id` не заденет `userId`.

3. Авторизуйтесь в bridge. Отдельного логина по паролю в bridge нет — только
   OAuth через Яндекс в браузере. Разовый бутстрап:
   - Войдите в bridge через браузер (пройдите Yandex OAuth).
   - В DevTools → Application/Storage → Cookies найдите cookie
     `bridgeRefreshToken` (домен API bridge, path `/api/v1/auth`) и
     скопируйте её значение.
   - Сохраните его в sync-cli:

     ```bash
     node dist/cli.js login <значение-cookie>
     ```

   Дальше sync-cli сам обновляет access-токен и перезаписывает у себя
   ротированный refresh-токен при каждой команде — повторный логин не нужен,
   пока refresh-токен не будет отозван (logout из bridge, истечение 7 дней
   бездействия и т.п.).

## Использование

На компьютере A:

```bash
node dist/cli.js push bridge
```

На компьютере B:

```bash
node dist/cli.js pull bridge
```

И симметрично в обратную сторону. `pull` отказывается перезаписывать
проект, если в нём есть незакоммиченные изменения (git working tree грязный) —
закоммитьте/застэшьте их или передайте `--force`.

`node dist/cli.js inbox [--channel issue] [--direction result|outbound] [--json]` —
показывает, какие посылки лежат в bridge (id, имя, taskKey, направление,
размер, возраст; новые сверху), ничего не скачивая и не удаляя, так что
следующий `pull-issue` их по-прежнему найдёт.

`node dist/cli.js doctor [name]` — проверяет, готова ли машина: для каждого
проекта (или указанного) путь-директория, словарь существует и разбирается,
`publicKeyPath`/`privateKeyPath` существуют и в формате PEM; глобально —
`bridge.apiUrl`, файл учётных данных bridge и GitLab-токен. По строке на
проверку (`[ok]`/`[warn]`/`[fail]`), код выхода 1 при любом `fail`. Только
локальные файлы, без сети; содержимое токенов и ключей не выводится.

Глобальный флаг `-v`/`--verbose` (до имени команды) включает debug-уровень
вывода (`src/log.ts`) — по умолчанию скрыт, обычные сообщения команд
(`log.info`/`log.warn`/`log.error`) показываются всегда, как и раньше.

## Режим issue

Помимо переноса всего дерева (`push`/`pull`), sync-cli умеет работать с одной
задачей GitLab: проект упаковывается в посылку `${projectId}-${iid}.subscription.zip`
(совместима с модулем Subscription в `reports`), её забирает агент на другой
машине, а результат возвращается обратно.

| Команда | Что делает |
| --- | --- |
| `login-gitlab <token>` | Сохраняет personal access token GitLab — `push-issue` берёт по нему заголовок и описание задачи. |
| `login-api-key <apiKey>` | Сохраняет персональный API-ключ bridge (Profile → API keys); для машины без человека лучше, чем `login`, т.к. не выдаёт себя за сессию пользователя. |
| `generate-keys <name>` | Генерирует пару RSA-4096 по `publicKeyPath`/`privateKeyPath` проекта — для шифрования в `push-issue`/`pull-issue`. |
| `push-issue <name> <projectId> <iid>` | Преобразует и грузит отслеживаемый проект как посылку для одной задачи GitLab. |
| `pull-issue <name> <projectId> <iid>` | Скачивает и преобразует последнюю посылку, адресованную этой задаче. |
| `gitlab-worker <name>` | Опрашивает GitLab: открытые задачи, назначенные на вас в этом проекте, которые ещё не отправлены, отправляет через `push-issue` — без ручного ввода id. |
| `agent-runner <name>` | Опрашивает bridge на посылки по задачам, запускает Claude Code в изолированном git worktree, пушит коммиты до/после в ветку на origin и возвращает результат в bridge. Словарь не используется — (де)обезличивание остаётся за `reports`. |
| `remove <name>` | Перестаёт отслеживать проект (обратное к `add`). |

Флаги:

- `--strict` (`push`, `push-issue`, `gitlab-worker`) — при находках leak-scan
  `push`/`push-issue` прерываются, а `gitlab-worker` пропускает такую задачу
  (без флага только предупреждение).
- `--dry-run` (`push-issue`) — ничего не отправлять: показать число файлов и
  изображений, имя посылки, шифруется ли она, первые 20 путей и находки
  leak-scan (GitLab читается, bridge и файлы состояния не затрагиваются). С
  `--strict` при находках по-прежнему завершается ошибкой.
- `--dry-run` (`push`) — ничего не отправлять и не обновлять сохранённый хеш:
  показать число файлов, размер архива, хеш, изменился ли он с прошлой отправки,
  первые 20 путей (все — с `-v`) и находки leak-scan. Вместе с `--strict` при
  находках по-прежнему завершается ошибкой.
- `-w, --watch <seconds>` (`pull-issue`, `gitlab-worker`, `agent-runner`) —
  опрашивать каждые `<seconds>` секунд. Для `pull-issue` — пока не появится
  результат, затем уведомление и выход; для `gitlab-worker` и `agent-runner` —
  вместо одного прохода.
- `--review` (`agent-runner`) — перед каждым запуском остановиться, чтобы
  просмотреть/отредактировать задачу и выбрать модель; несовместим с `--watch`.
- `-f, --force` — `push`: отправить, даже если хеш содержимого не изменился;
  `pull`: даже при грязном git-дереве или неизменном хеше; `pull-issue`: даже
  при грязном git-дереве; `generate-keys`: перезаписать существующие ключи.

Пример (машина A отправляет задачу, ждёт результат):

```bash
node dist/cli.js login-gitlab <gitlab-token>
node dist/cli.js generate-keys bridge
node dist/cli.js push-issue bridge 123 45 --strict
node dist/cli.js pull-issue bridge 123 45 --watch 30
```

На машине с агентом: `node dist/cli.js agent-runner bridge --watch 30`.

Запуск Claude ограничен по времени: `SYNC_AGENT_TIMEOUT_SEC` (по умолчанию 1800 с).
По истечении — `SIGTERM`, через 10 с `SIGKILL`, ошибка `claude timed out after Ns and
was killed` попадает в лог, worktree остаётся для разбора, а `--watch` идёт дальше.

Подробнее о сценариях — [`docs/workflows.md`](../docs/workflows.md), о форматах
state-файлов — [`ECOSYSTEM.md`](../ECOSYSTEM.md).

## Прокси

Если сеть требует прокси для выхода в интернет (как у `reports`), укажите
`HTTPS_PROXY`/`HTTP_PROXY` — sync-cli подхватит их так же, как это делает
`reports/packages/server/src/utils/setup-proxy.ts`:

```bash
HTTPS_PROXY=http://user:pass@proxy.example.com:8080 sync-cli push bridge
```

## Ограничения текущей версии

- Dot-файлы (`.env.example`, `.gitlab-ci.yml`, `.eslintrc` и т.п.) и
  dot-папки не подхватываются масками вроде `**/*` (`dot: false` в
  `walkProjectFiles`), но попадают в `push`, если указать их в `include`
  явно (`.env.example`, `.github/**`) — делайте это осознанно. Симлинки
  пропускаются.
- Только удаления файлов не переносятся: `pull` добавляет/обновляет файлы,
  присутствующие в архиве, но не удаляет локальные файлы, которых в архиве
  нет.
- Одна незабранная посылка на канал: если `push` выполнить дважды подряд без
  `pull` между ними, на бридже успеет накопиться несколько версий — заберётся
  только самая свежая (см. `pack.ts`/`pull.ts`), более старая останется
  висеть в хранилище нескачанной.
- Авторизация — через один и тот же bridge-аккаунт на обеих машинах.
