# Распределённая система: три слоя, автоматический переход, локальная LLM

Решение для владельца, не инструкция по установке. Продолжает [ha-dr-plan.md](ha-dr-plan.md) (там же — инвентаризация, бэкапы, сторож и
failover по DNS для схемы «Selectel + Pi»); здесь схема другая: **основной слой — дом, облако — последний**. Пометки: **[факт]** — видно в репозитории или
измерено, **[оценка]** — моё суждение, **[не проверено]** — нужно проверить до решения. Цен и тарифов в документе нет: я их не проверял.

## 1. От чего защищаемся (по опыту этой недели)

| Что случилось | Слой, который это закрывает |
|---|---|
| 2026-10-27: входящие 80/443 на домашнем роутере пропадали и возвращались после `restart_firewall`; весь внешний доступ — одна точка | вход, не зависящий от домашнего NAT (§3, этап 1) |
| Платы 9+ часов не отчитывались, ни один сторож не мог сказать об этом снаружи | независимые наблюдатели в 3 местах (§5) |
| Дом = один роутер, один провайдер, один IP, одна комната | второй дом, облако |
| Лимиты и отзыв токенов Claude: 32 ошибки из 318 за неделю [факт, Worker → ошибки] | локальная модель как запасной исполнитель (§9) |

Требования владельца, которые я принимаю как данность: три слоя (дом 1 → дом 2 → облако), **автоматический** переход при отказе рабочего слоя,
реализация растянута на 6–12 месяцев, каждый этап должен приносить пользу сам по себе.

## 2. Ключевая идея: лидерство = первичный Postgres

Главная трудность распределённой системы здесь — **не дать двум площадкам работать как основным**. Backend bridge нельзя запускать в двух экземплярах
[факт, `ha-dr-plan.md` §8.4]: в нём планировщики Improve (`@Interval`), long-polling Telegram (второй получит HTTP 409), очистка вложений. Поэтому:

> **Активна ровно та площадка, на которой Postgres — первичный (writable).** Остальные держат реплику только для чтения, и их backend не запускает
> планировщики и опрос Telegram.

Это даёт три вещи сразу: (1) «кто главный» определяется одним механизмом (выбор лидера Postgres), а не договорённостью нескольких сторожей; (2) старый
первичный, вернувшись из отказа, не может писать — он понижается до реплики; (3) вход и воркеры просто идут туда, где ответ `leader`.

Что нужно в коде [оценка, 2–3 дня]: эндпоинт `GET /api/v1/health/leader` (200 только если БД не в `pg_is_in_recovery()`), и запуск планировщиков/Telegram
только пока backend — лидер (проверка при старте и раз в несколько секунд). Остальное — инфраструктура.

## 3. Варианты

### Вариант A — «как в ha-dr-plan»: DNS-переключение, ручное подтверждение
Сторож проверяет основную площадку, при отказе просит подтверждение в Telegram и меняет DNS (TTL 60 с). Просто, но: DNS-кэши (минуты), требуется публичный IP
у каждой площадки (вторая квартира может быть за CGNAT), и эта неделя показала, что **домашний входящий канал сам хрупкий** [факт]. Остаётся как
запасной механизм, не как основной.

### Вариант B — облачный «входной слой» + WireGuard (рекомендую как основу)
Маленькая облачная ВМ — постоянная публичная точка входа. Обе квартиры **сами подключаются к ней** по WireGuard (исходящее соединение, пробросы портов не нужны,
CGNAT не мешает). На ней Caddy/HAProxy с активными проверками направляет трафик на первый здоровый приёмник в порядке приоритета:

```
пользователь ──► облачный вход (Caddy, health /api/v1/health/leader)
                      │  WireGuard (исходящие из квартир)
                      ├─► дом 1 (Pi, приоритет 1)
                      ├─► дом 2 (приоритет 2)
                      └─► облачный стек (приоритет 3, холодный/тёплый)
```

- Переключение входа — секунды (проверки каждые 2–5 с), без DNS и без TTL [оценка].
- **Решает именно ту поломку, что была:** входящий проброс на домашнем роутере перестаёт быть единственным путём [факт: падал 27.10].
- Минусы: вход сам становится точкой отказа → два входа у разных провайдеров (две A-записи; браузер сам пробует следующий адрес при отказе TCP-соединения) [оценка];
  провайдер облака технически видит трафик, если терминирует TLS → можно пропускать TLS на уровне TCP (SNI) и терминировать в домашнем слое [оценка].
- Что в репозитории пригодится: Caddyfile уже есть (`infra/bridge-pi/Caddyfile`), реплика БД и Garage — тоже.

### Вариант C — выбор лидера с кворумом (Patroni + etcd или аналог)
Postgres под управлением Patroni, голоса кворума в трёх местах: дом 1, дом 2, облако. Потеря любого одного места не ломает кворум; бывший лидер понижается сам.
Даёт **автоматический** переход без человека и без split-brain. Цена: больше движущихся частей (etcd, Patroni), чувствительность к задержкам между квартирами,
и вам нужно уметь это чинить. Более простая лестница вместо сразу C [оценка]:

| Ступень | Что принимает решение | Когда включать |
|---|---|---|
| 1. Ручной promote | вы, по сообщению сторожа (как сейчас в `failover.sh`) | сразу |
| 2. Полуавтомат | два независимых наблюдателя согласны → promote после вашей кнопки | после первых учений |
| 3. Автомат | Patroni/etcd (кворум 3 места) | после 3+ успешных учений и 2–3 месяцев без ложных срабатываний |

### Что не делать
- **Один Swarm через интернет** между квартирами: задержки и split-brain, уже отвергнуто в плане [факт, `ha-dr-plan.md` §0]. На каждой площадке свой независимый стек.
- **Активный-активный** (две записывающие площадки): не нужен этому масштабу и ломает планировщики.
- **Синхронная репликация между квартирами** по умолчанию: пока второй дом недоступен, запись встанет. Асинхронная с контролем лага; синхронная — только на один
  резерв и с таймаутом [оценка].

## 4. Слои

| Слой | Что | Роль | Состояние при норме |
|---|---|---|---|
| **1. Дом 1** | 4× Pi 5 (white основной, red реплика, blue менеджер, green воркер) [факт] | рабочий | активен, лидер |
| **2. Дом 2** | оборудование для резерва (см. ниже) | резерв «тёплый» | реплика БД, стек остановлен/read-only |
| **3. Облако** | малая ВМ у провайдера: вход + реплика + бэкапы | последний слой и входной слой | вход активен всегда; стек холодный |

**Оборудование слоя 2** [оценка, выбор за вами]: достаточно 2 устройств, не обязательно Pi. Вариант 1: пара Pi 5 8 ГБ с NVMe (одинаковый образ с домом 1, меньше
нового). Вариант 2: один мини-ПК (например класса N100/N150) на amd64 + небольшой ИБП — дешевле по числу устройств, но образы нужны под обе архитектуры (они уже
мультиархитектурные [факт, GHCR]). Обязательно: ИБП, проводной интернет, отдельный провайдер от дома 1. **[не проверено]:** тип подключения во второй квартире
(статический IP? CGNAT?) — при варианте B это не критично.

**Облако (слой 3):** 1–2 vCPU / 2–4 ГБ [оценка по PI5-CAPACITY.md §8: стек занимает ≈200 МБ]. Требования к провайдеру — как в `PI5-CAPACITY.md` §8: другой домен отказа,
публичный статический IP, оплата, которую вы можете совершить [проверить по каждому кандидату].

## 5. Наблюдатели и согласие

Решение «слой упал» принимается только при согласии минимум двух независимых наблюдателей из разных мест (защита от «упал мой канал, а не сервер»):

- облачный вход проверяет оба дома (health-check);
- дом 2 проверяет дом 1 через WireGuard и через публичный адрес;
- внешний пробник на стороне GitHub [факт, PR #1035] — третье мнение и канал оповещения, не зависящий от вашей инфраструктуры;
- Telegram — для оповещений; запасной канал — issue `outage` (почта GitHub).

Гистерезис: переход после N подряд неудачных проверок (≈ 60–90 с), возврат — не раньше чем через 10–15 минут стабильной работы и **по умолчанию вручную** (перенос
данных обратно — решение человека, `ha-dr-plan.md` §8.3).

## 6. Данные

| Что | Как реплицируется | Потеря при переходе [оценка] |
|---|---|---|
| Postgres | потоковая репликация (слоты репликации) в дом 2 и облако; асинхронно | секунды–минута |
| Файлы (uploads, вложения, парсели) | Garage с зонами по площадкам, либо облачный S3 как общий + зеркало [проверить поведение Garage на задержках между квартирами] | ноль/минуты |
| Образы | GHCR, каждая площадка тянет сама | нет |
| Секреты и ключи (age, `CREDENTIALS_ENC_KEY`) | зашифрованная копия на каждой площадке + одна офлайн-копия; без ключа переход невозможен [факт, `ha-dr-plan.md` §10] | — |
| Бэкапы | как сейчас + в облаке; восстановление проверяется по расписанию [факт, `restore-check.sh`] | — |

RPO целевой: **минуты** (раньше в плане было «до суток»). Это пересмотр требования — подтвердите.

## 7. Воркеры, VPN, Telegram

- Воркеры — без состояния; они опрашивают bridge по имени и поэтому автоматически работают с активной площадкой [факт]. Пары воркеров можно держать в каждом слое.
- Telegram: один long-polling — у лидера. Прокси `vpn-client` должен быть там, где лидер [факт: нужен для Telegram].
- VPN-серверы (две ВМ, уже есть [факт]) могут стать кандидатами для облачного входа вместо новой ВМ: у них нет данных и уже есть доступ по ключам. **Оговорка:** серверы слабые
  (705 МБ памяти [факт]), и вход они не потянут вместе с VPN — лучше отдельная ВМ [оценка].

## 8. План на 12 месяцев (каждый этап ценен сам по себе)

Остановиться можно после любого этапа. Первые два уже закрывают класс сбоев, который был на этой неделе.

| Месяцы | Этап | Результат | Оценка усилий [оценка] |
|---|---|---|---|
| 0–1 | **0. Основание**: роутер/провайдер (диагностика входящих, замена роутера по `PI5-CAPACITY.md` §12.1), внешний пробник (#1035), учение «выключить white» с замером RTO, ИБП | знаем реальные RTO/RPO; дом 1 стабилен | 2–3 недели |
| 1–3 | **1. Облачный вход (слой 3, вариант B)**: ВМ + WireGuard + Caddy c health `/health/leader`; дом 1 подключается исходящим туннелем; DNS на облачный вход (две A-записи — вторым входом позже) | вход не зависит от домашнего NAT; переключение входа — секунды | 3–4 недели |
| 3–5 | **2. Лидерство в коде и облачная реплика**: `health/leader`, планировщики только у лидера, реплика Postgres и бэкапы в облаке, ручной promote в облаке | автономный последний слой, ручное восстановление за минуты | 3–4 недели |
| 5–8 | **3. Дом 2**: оборудование, WireGuard, реплика БД, Garage-зона, тёплый стек; ручной promote дом 1 → дом 2 | второй дом готов принять нагрузку; учения раз в месяц | 4–6 недель |
| 8–10 | **4. Полуавтомат**: согласие двух наблюдателей + кнопка в Telegram; приоритеты входа 1→2→3 | переход слоя на слой по кнопке за ≤ 2–3 мин | 3–4 недели |
| 10–12 | **5. Автомат**: Patroni/etcd c кворумом из 3 мест (или остаться на полуавтомате, если ложные срабатывания не исключены); автоматический возврат — опционально | переход без человека | 4–6 недель |
| параллельно, с месяца 3 | **Локальная LLM** (§9) | запасной исполнитель задач, не зависящий от лимитов Claude | см. §9 |

Каждый этап заканчивается **учением**: реально выключить слой и записать RTO, RPO и что пошло не так. Без учений схема остаётся «на бумаге».

## 9. Отдельно: локальная LLM

### 9.1. Зачем и чего не ждать
Зачем [факт/оценка]: (1) лимиты и отзыв OAuth-токенов Claude — основная причина ошибок воркеров за неделю; (2) часть работы вообще не требует лучшей модели:
оценка предложений анализа, сортировка/выжимка логов, сводки PR, Chat; (3) не зависит от VPN и внешних провайдеров (важно при схеме с одним каналом).
Чего не ждать: локальные открытые модели в агентной правке кода, как правило, заметно слабее Claude [оценка, моё общее знание, не измерено на вашем репозитории].
Поэтому не «заменить Claude», а **гибрид**: локальная модель — для дешёвых и запасных задач; Claude — для написания патчей; при исчерпании лимита (как pi-red сейчас [факт]) —
запасной исполнитель.

### 9.2. Что уже есть в проекте
Воркер умеет запускать задачи у OpenAI-совместимых провайдеров (gpt/deepseek/qwen) [факт, `worker/src/chatRunners/openAiCompatibleChat.ts`, `CLAUDE.md`]. Локальные серверы
(Ollama, llama.cpp server, LM Studio, vLLM) отдают такой же API → добавляется провайдер `local` с базовым адресом и без ключа. **Ограничение:** этот раннер не даёт
модели оболочки и правки файлов («no shell tool») — то есть подходит для чата, оценки, сводок, но не для правок кода. Для правок нужен агентный каркас
(например Claude Code через совместимый прокси, либо открытые агенты: aider, OpenHands, opencode и т. п.) [не проверено вместе с вашим воркером].

### 9.3. Железо
| Вариант | Что тянет | Замечания |

### 9.4. Как решить без самообмана (оценочный стенд)
1. Взять 20 уже влитых PR/issue (есть ~170 автоматических [факт]) и 20 типовых задач анализа/сводок.
2. Прогнать их через 2–3 локальные модели и через Claude; сравнить: проходит ли CI, нужно ли ручное исправление, время, расход памяти.
3. Решение принимается по доле задач, закрытых без вмешательства: порог (например ≥ 60 % от Claude на «лёгких» классах) задаёте вы.
4. Модели называть конкретно не буду: мои сведения о них могут устареть (граница знаний — июнь 2026); брать актуальные кодовые модели семейств Qwen-Coder, DeepSeek, gpt-oss,
   GLM, Devstral и сверять с бенчмарками на момент решения [не проверено].

### 9.5. Где живёт в слоях
Модель без состояния, поэтому в схему надёжности не входит: если локальный узел недоступен — воркер идёт во внешнего провайдера. Размещать в доме 1 (рядом с воркерами),
не на Pi. Отдельный воркер с провайдером `local` и ограничением «только задачи класса X».

## 10. Риски и честные оговорки
- Это существенный объём сопровождения для личного инструмента; каждая ступень добавляет то, что нужно уметь чинить. Поэтому этапы и точки остановки.
- Автомат без учений опаснее ручного режима: ложное срабатывание с разделением лидерства хуже простоя. Автомат включаем только после учений и гистерезиса.
- Основной риск вашего плана на практике — **домашний канал и роутер**, а не отсутствие слоёв; этап 0–1 важнее остальных.
- Оценки времени — мои, без привязки к вашей занятости; в таблице §8 указано только рабочее время.
