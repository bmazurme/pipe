### A. Срочно (проверено 2026-10-12)

> **Статус 2026-10-13:** TTL выставлен 600 с (минимум панели reg.ru); `bridge` и `api.bridge` указывают на домашний адрес `89.207.218.46`, сервис
> отвечает с Pi. Домашний IP **статичен** (подтверждено владельцем), а при переключении между платами адрес не меняется (плавающий `192.168.50.10`), поэтому автообновлятор DNS через API reg.ru нужен только при переходе на внешнюю площадку (§11).

Прямо сейчас `ntlstl.dev`, `bridge.ntlstl.dev` и `api.bridge.ntlstl.dev` указывают на
**один адрес `89.169.132.49` — это Yandex Cloud** (whois: `RU-YANDEXCLOUD`), и все три
не отвечают (таймаут). DNS зоны `ntlstl.dev` хостится на **`ns1.reg.ru`/`ns2.reg.ru`** —
то есть **не в Яндексе, это хорошо**: переключать адрес можно, не дожидаясь Яндекса.

Но у записей **огромный TTL**:

| Имя | TTL |
|---|---|
| `bridge.ntlstl.dev` | 86 399 с (≈ 24 ч) |
| `ntlstl.dev` | 28 400 с (≈ 7,9 ч) |
| `api.bridge.ntlstl.dev` | 20 438 с (≈ 5,7 ч) |

Последствие: после смены адреса часть пользователей и резолверов будет видеть
старый адрес **до суток**. Поэтому, **ещё до любых работ**:

1. В личном кабинете reg.ru (DNS-зона `ntlstl.dev`) поставить TTL **300 с** у
   трёх записей (позже, после проверки, — 60 с). Уменьшение TTL заработает только
   по истечении **старого** TTL — чем раньше, тем лучше.
2. Выяснить, **включён ли у reg.ru доступ к API** для зоны (он нужен сторожу для
   автоматической смены записей; обычно включается в настройках аккаунта и
   привязывается к IP-адресу — **проверьте в кабинете**; я это проверить не мог).
   Запасной вариант без API: делегировать зону на Selectel DNS (бесплатный
   DNS-хостинг с API) сменой NS у регистратора — тоже не раньше, чем будет
   понятен TTL записей NS.
3. Записей `CAA`, `MX`, `TXT` у домена сейчас нет — менять почту не придётся.

### C. Selectel: минимальный тариф

Я смог проверить на сайте Selectel одну цифру: самый дешёвый облачный сервер
стандартной линейки — **от 948,50 ₽/мес** (конфигурация на странице не указана,
есть и «shared»-линия с оплатой части vCPU 10/20/50 % — для продакшена не
подходит). Остальных цен (управляемая БД, floating IP, S3) страницы без выбора
региона не показывают, **поэтому суммы ниже не указываю — посчитайте в
калькуляторе Selectel**, в нём всё перечислено.

Три уровня, от дешёвого к надёжному:

| Уровень | Что заказать | Что даёт |
|---|---|---|
| **Минимум (рекомендую начать так)** | 1 облачная ВМ, **2 vCPU / 4 ГБ / 40 ГБ SSD**, стандартная линейка, 1 публичный IP; Postgres **в Docker на этой же ВМ**; S3-бакет `bridge-backups` (и `bridge-uploads`, когда будет S3-драйвер); Selectel DNS (бесплатный) — по желанию | Возвращает сервис (этап 3) и принимает бэкапы. Отказ ВМ = переключение на Pi (RTO минуты, потеря ≤ суток — ваши требования). **Не** защищает от отказа одной ВМ без переключения |
| **Рекомендуемый** | то же + **Managed PostgreSQL**, одиночный узел минимального размера (бэкапы провайдера в придачу) | БД не на вашей ВМ, проще восстановление |
| **Полный (позже)** | 2 ВМ в разных зонах + Managed PostgreSQL HA + балансировщик/floating IP | автоматический HA внутри Selectel (этап 9) |

Почему «Минимум»: у вас уже есть тёплый резерв на Pi и требование RTO — минуты,
RPO — сутки. Дорогой Managed HA на старте не нужен; его можно включить позже, не
меняя остальную схему. Ёмкость ВМ — с запасом на pgAdmin и `ntlstl-front`
(остальные стеки — позже, §11).

## 0. Коротко

- **Было (до 2026-10-12)** — всё на одной ВМ в Yandex Cloud (одиночный узел Swarm), образы в Yandex Container Registry, вход только
  через Yandex OAuth: недоступность Яндекса = нет ни сервиса, ни деплоя, ни входа.
- **Сейчас** — сервис работает на Raspberry Pi (white, остальные платы держат реплику БД, S3 и worker), образы в GHCR, деплой с
  проверкой и откатом идёт сам; Яндекс для работы не нужен. См. «Что есть сейчас» выше.
- **Цель** — три независимых «домена отказа»: **Selectel** (основная площадка),
  **4× Raspberry Pi 5 дома** (резерв + хранение бэкапов) и, когда Яндекс
  вернётся, **Yandex Cloud** (третья копия, не основная).
- **Требования владельца:** восстановление — **минуты**; потеря данных — не
  более **суток** (бэкап **раз в день**, 15-минутных копий не нужно, но это
  зафиксировано здесь); хранится **только последняя копия** (см. §6 — как это
  сделать безопасно); вход через **Yandex сохраняется**, добавляется **GitHub
  OAuth**, способы входа включаются и выключаются в профиле, **минимум один
  всегда включён**.
- **Переключение — с ручным подтверждением** (решение владельца): сторож сам
  обнаруживает отказ и присылает в Telegram запрос «Переключить?» — отказ
  подтверждается кнопкой/командой; полностью автоматический режим можно включить
  позже, после учений.
- **Принципиальные решения:**
  1. Две площадки — **два независимых Swarm**, не один кластер через интернет
     (задержки и split-brain на домашнем канале недопустимы).
  2. Резерв **тёплый**: стек развёрнут на Pi, база ночью восстанавливается из
     свежего дампа, **бэкенд остановлен** до переключения (у него есть
     планировщики и long-polling Telegram — два живых экземпляра подерутся, см. §8).
  3. Переключение — **DNS с TTL 60 с**, решение принимает сторож, которого
     нельзя положить вместе с основной площадкой.
  4. Образы — в **GHCR** (мультиархитектурные amd64+arm64) + зеркало в реестре
     Selectel; Яндекс из пути деплоя убирается.

### 3.2. Топология и питание

- Каждый коммутатор питает **2 Pi** (≈ 10–20 Вт на Pi с NVMe под нагрузкой —
  с запасом в бюджете). Не вешать четыре Pi на один коммутатор.
- Pi-1, Pi-2 → коммутатор A; Pi-3, Pi-4 → коммутатор B; порт 5 каждого
  коммутатора — аплинк: A → роутер, B → A (или оба в роутер, если свободны
  порты и нет петель/STP-проблем: неуправляемым коммутаторам петлю делать нельзя).
- Дом — **единая точка отказа по питанию и каналу**, поэтому дальше про ИБП и LTE.

### 3.3. Что докупить

## 4. Подготовка Raspberry Pi («почистить и настроить»)

> SSH-ключи и адреса — позже (по договорённости). Шаги ниже оформляются как
> **Ansible-плейбук** в `infra/pi/` (после получения доступов), чтобы любую
> плату можно было переустановить за минуты.

1. **Образ.** **Ubuntu Server 24.04 LTS (arm64)** — тот же дистрибутив, что на плате
   сейчас и (планово) на ВМ Selectel, один набор пакетов и привычек. Поддержка до
   2029 г. (26.04 LTS, вышедший 23.04.2026, — допустимая альтернатива с поддержкой до
   2031 г.; **не** промежуточные 25.04/25.10, они уже без обновлений). Образ — через
   Raspberry Pi Imager на NVMe (NVMe в USB-корпусе/адаптере или загрузка с microSD и
   запись на NVMe). Имена `pi-1`…`pi-4`.

   *Почему в первой версии плана был Raspberry Pi OS Lite:* я не знал, что платы на
   Ubuntu, и взял «по умолчанию» штатную ОС Pi. Требования к ней нет — Ubuntu Server LTS
   подходит не хуже (NVMe-загрузка, Docker, arm64 поддерживаются); менять ОС ради ОС не нужно.
2. **Загрузка с NVMe.** Обновить EEPROM (`rpi-eeprom-update` из пакета `rpi-eeprom`; на Ubuntu
   `vcgencmd` ставится из `libraspberrypi-bin`, пользователю нужна группа `video`), задать
   `BOOT_ORDER` с приоритетом NVMe, включить PCIe (`dtparam=pciex1`;
   Gen3 — неофициально, по умолчанию оставить Gen2, если нет нужды в скорости).
3. **Разметка NVMe 128 ГБ:** ≈ 32 ГБ система + Docker; остальное — данные
   (Postgres `/var/lib/postgresql` и Garage `/var/lib/garage` на отдельной
   файловой системе ext4).
4. **Безопасность:** вход только по SSH-ключам, `PasswordAuthentication no`,
   отдельный пользователь без пароля root, `ufw` (SSH — только из LAN и из
   WireGuard; 80/443 — на тех узлах, что принимают трафик), `fail2ban`,
   `unattended-upgrades`, `chrony` (время критично для TLS/токенов).
5. **Сеть:** DHCP-резервации по MAC (или статика) `pi-1..4`; на роутере проброс
   80/443 на виртуальный адрес (keepalived VIP между Pi-1/Pi-2) и UDP-порт
   WireGuard.
6. **WireGuard** между домом и Selectel (частный overlay `10.77.0.0/24`):
   закрытый канал для бэкапов, мониторинга и административного доступа; не
   использовать его как транспорт для Swarm.
7. **Docker + Swarm A:** `pi-1`, `pi-2`, `pi-3` — managers (кворум 2 из 3),
   `pi-4` — worker. Сеть overlay только внутри дома.
8. **Наблюдаемость:** node_exporter, `smartctl`/`nvme smart-log` с алертом на
   износ, температуру и троттлинг (`vcgencmd get_throttled`).
9. **ИБП:** NUT на Pi-1 (master), остальные — клиенты; при остатке заряда <
   X мин — упорядоченное выключение (сначала Pi с Postgres).
10. **Гигиена хранилища:** `log2ram` не нужен (NVMe), но ограничить размер
    журналов Docker (`max-size`, как уже сделано в стеке).

## 6. Бэкапы

### 6.1. Политика

| Параметр | Значение |
|---|---|
| Что | Postgres (`pg_dump -Fc`), объекты S3 (`bridge-uploads`), конфигурация (список секретов — §10, **без** значений) |
| Как часто | **раз в сутки**, 03:00 по Москве (вне пиков). **Не** чаще: допустимая потеря — до суток (решение владельца, 2026-10-12) |
| Сколько хранить | **только последнюю копию** на каждой площадке (решение владельца) — **при условии «сначала проверить, потом заменить»** |
| Куда | Selectel S3 (`bridge-backups/latest`) + Pi (NVMe `/srv/backups/latest`) + позже Yandex Object Storage |
| Шифрование | на стороне клиента (`age`), ключ — отдельно от данных (§10); в S3 лежит только шифртекст |
| Проверка | каждая копия проверяется до замены (`pg_restore --list`, контрольная сумма, размер не меньше 50 % предыдущей) |
| Алерт | возраст последней копии > 26 ч, ошибка проверки, рост/падение размера > 30 % |

**Почему «проверить, потом заменить», а не «просто перезаписать».** Если
ежесуточный дамп случайно окажется пустым или битым, хранение «только последней»
затрёт и последнюю хорошую копию. Поэтому скрипт пишет дамп во **временное имя**,
проверяет, и лишь затем атомарно подменяет `latest`. Это даёт ту же «одну копию»
по занимаемому месту, но без этого риска. Если когда-нибудь понадобится, один
параметр `KEEP=N` включит хранение N последних (рекомендация — 3; стоит копейки).

### 6.2. Скрипт (набросок, `infra/backup/backup.sh`)

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F)                 # логирование; хранится только latest
TMP=$(mktemp -d); trap 'rm -rf "$TMP"' EXIT

pg_dump --format=custom --no-owner "$DATABASE_URL" -f "$TMP/db.dump"
pg_restore --list "$TMP/db.dump" >/dev/null                 # структура читается
[ "$(stat -c%s "$TMP/db.dump")" -ge "$MIN_BYTES" ]          # не пустой
age -r "$AGE_RECIPIENT" -o "$TMP/db.dump.age" "$TMP/db.dump"
sha256sum "$TMP/db.dump.age" > "$TMP/db.dump.age.sha256"

# заливаем под временным именем, затем подменяем latest (атомарно на стороне S3 — copy+delete)
rclone copyto "$TMP/db.dump.age" selectel:bridge-backups/incoming/db.dump.age
rclone copyto "$TMP/db.dump.age.sha256" selectel:bridge-backups/incoming/db.dump.age.sha256
rclone check "$TMP" selectel:bridge-backups/incoming --include "db.dump.age*"
rclone moveto selectel:bridge-backups/incoming selectel:bridge-backups/latest
echo "$STAMP ok" | tee -a "$LOG"
```

Pi забирает копию сам (**pull**, чтобы взлом основной площадки не добрался до
резерва): `rclone sync selectel:bridge-backups/latest /srv/backups/latest`
(тоже с проверкой). Для файлов: `rclone sync selectel:bridge-uploads
garage:bridge-uploads` ежедневно.

### 6.3. Pi как хранилище бэкапов и S3

Роль Pi-кластера в хранении:

1. **Копия дампа БД** — файл `latest` на NVMe двух Pi (pi-1 и pi-2).
2. **Зеркало файлов S3 — Garage** (лёгкое S3-совместимое хранилище на Rust для
   небольших кластеров, arm64, репликация фактором 3 по узлам). Вариант MinIO
   возможен, но модель поставки его сообществу менялась в 2025 году —
   **проверить текущее состояние лицензии/сборок** перед выбором.
3. Ёмкость: 4 × ≈ 90 ГБ данных при репликации 3 ≈ **120 ГБ полезного**
   — **сверить с реальным размером `uploads`** (§1, команда `du`).
4. **NAS WD EX2 Ultra (2 × 2 ТБ, RAID 1)** — большая «холодная» копия: ежедневная
   `rsync` с Pi (**pull с Pi**, по SSH/NFS, только внутри локальной сети) дампа `latest` и
   зеркала файлов. Это снимает вопрос ёмкости (2 ТБ против ≈ 120 ГБ Garage), но у
   устройства нет S3 и оно старое: **не открывать наружу**, не использовать как единственную
   копию, следить за SMART дисков. RAID 1 защищает от отказа диска, а не от ошибок
   и удаления — поэтому дамп «проверить, потом заменить» остаётся обязательным.
5. NVMe — расходный материал: смотреть износ (`nvme smart-log`), алерт при
   >80 % и **запас: один NVMe в шкафу**.

Если `uploads` не помещается — приоритет у БД и последних файлов; остальное
хранить только в Selectel S3 + Yandex (позже).

## 7. Что меняется в коде и конфигурации проекта

### 7.1. Файловое хранилище → S3

`StorageService` и вложения чата (`bridge/apps/backend/src/chat/…`) пишут в
`/app/uploads`. Нужен драйвер S3 (`@aws-sdk/client-s3`), переключаемый
переменной `STORAGE_DRIVER=disk|s3`, **с миграцией существующих файлов** и
чтением как с диска (на время перехода), так и из S3. Два экземпляра
приложения (основной и резервный) смотрят в разные бакеты/endpoint: резервный —
в Garage-зеркало; при переключении он уже имеет файлы суточной давности.
Оценка: 2–3 дня + тесты.

### 7.2. Бэкенд: готовность к «холодному» резерву

- `replicas: 0` на Pi до переключения (в стеке резерва — отдельный override).
- Миграции при старте запускаются автоматически (`migrationsRun: true`) — на
  свежем дампе безопасно, но **версия образа резерва должна совпадать с
  версией на момент дампа** (резерв разворачивается теми же SHA, что и основной,
  CI деплоит на обе площадки одним прогоном).
- Секреты те же (`JWT_SECRET`, `REFRESH_JWT_SECRET`, `CREDENTIALS_ENC_KEY` — см.
  §10), поэтому **сессии пользователей переживают переключение**, а
  зашифрованные данные читаются.

### 7.3. CI/CD (`.github/workflows` — **защищённый путь, изменения только с
вашего согласия**)

- сборка `docker buildx` на `linux/amd64,linux/arm64`, публикация в GHCR (+ копия в
  реестр Selectel);
- шаг деплоя на Selectel (SSH на менеджер) и отдельный шаг на Pi (SSH через
  WireGuard/по внешнему адресу; допустимо падение этого шага без блокировки
  основного);
- для `ntlstl-front` — тот же шаблон, `deploy.yml`/`docker-compose.yml`;
- в `deploy-bridge.yml` убрать `YC_SA_JSON_CREDENTIALS`/`yc-cr-login`
  (когда реестр переехал).

### 7.4. Вход: Yandex + GitHub OAuth, управление способами входа

**Требования:** сохранить Yandex OAuth; добавить GitHub OAuth; в профиле можно
отключить способ входа; **минимум один способ включён всегда**.

Модель данных (миграция):

```
auth_identities
  id, userId (FK users, ON DELETE CASCADE)
  provider        'yandex' | 'github'
  providerUserId  varchar   -- стабильный id у провайдера (не email)
  email           varchar null   -- как сообщил провайдер, для показа
  enabled         boolean default true
  createdAt, lastUsedAt
  UNIQUE (provider, providerUserId)
  UNIQUE (userId, provider)
```

Правила:

1. **Инвариант на сервере** (не только в UI): отключить или отвязать способ
   можно, только если после операции у пользователя остаётся ≥ 1 включённый
   способ (проверка в транзакции с блокировкой строк пользователя —
   защита от гонки «отключаю оба одновременно»). Ответ — `409`.
2. Вход через **отключённый** способ запрещён (`403`, понятное сообщение).
3. **Привязка** нового способа — только из уже авторизованной сессии
   (профиль → «Подключить GitHub»), с параметром `state` (CSRF) и проверкой, что
   провайдерский аккаунт не привязан к другому пользователю. **Сопоставление по
   email — только если провайдер сообщил подтверждённый email**, и только для
   первичной привязки существующего пользователя по списку `EMAILS`; иначе —
   только явная привязка.
4. Существующие пользователи: миграция создаёт `auth_identities` для
   текущей связки Yandex (по сохранённому id/email) — вход не ломается.
5. Список `EMAILS` (allowlist) сохраняется: GitHub-аккаунт допускается, только
   если его подтверждённый email в списке либо он явно привязан.
6. Redirect URI (оба провайдера) — на **общий домен** `api.bridge.ntlstl.dev`: он
   одинаков на обеих площадках (DNS переключается), поэтому настройки OAuth не
   надо менять при failover.

API/UI:

- `GET /api/v1/auth/identities` — список способов, состояние, `lastUsedAt`;
- `POST /api/v1/auth/identities/:provider/enable|disable`, `DELETE …/:provider`;
- `GET /api/v1/oauth/github`, `…/github/redirect` (по образцу `oauth.controller.ts`);
- профиль → секция «Способы входа»: переключатели, кнопка «Подключить», подсказка
  «нельзя отключить последний способ» (и сервер это гарантирует);
- кнопка «Войти через GitHub» на странице входа; доступные способы показывает
  `GET /api/v1/oauth/providers` (чтобы при отключении провайдера на сервере
  кнопка пропадала).

Оценка: 3–4 дня с тестами (бэкенд — стратегия `passport-github2`, миграция,
инвариант и гонка; фронтенд — секция профиля и кнопка входа).

### 7.5. Резервные ключи доступа

Вход по API-ключам (машинный) остаётся независимым от OAuth. Добавить в
профиль возможность создать **ключ аварийного доступа** (долгоживущий, видимый
один раз) — на случай, когда ни Яндекс, ни GitHub недоступны одновременно.

## 8. Переключение (failover) и возврат (failback)

### 8.1. Сторож (watchdog) на Pi

Работает **на Pi**, потому что именно Pi переживает отказ Selectel; но он не
должен быть единственным сторожем — второй, внешний, независимый (например,
бесплатный облачный мониторинг/проверка с отдельной площадки или с VPS у
третьего провайдера), и они сверяются: **решение о переключении — только если
оба согласны** (или вручную). Это защита от ситуации «упал домашний канал, и Pi
решил, что умер Selectel».

Проверки (каждые 20 с): `GET /api/v1/health` через публичный адрес, TCP 443,
доступность БД (из health-ответа), статус ВМ Selectel через API. Порог:
**4 подряд неуспешных (≈ 80 с)** с двух точек наблюдения.

**Режим первого этапа — ручное подтверждение (решение владельца).** Сторож не
переключает сам: он присылает в Telegram сообщение «Selectel недоступен 80 с —
переключить на дом?» с кнопками **Переключить** / **Подождать 10 мин** /
**Игнорировать**. Только после «Переключить» выполняется `promote.sh`. Если вы не ответили
за N минут — повторное напоминание, но не самостоятельное действие. Автоматический режим
(`PROMOTE_MODE=auto`) включается отдельным решением после нескольких успешных учений.
Команда `/promote` в боте дублирует кнопку; доступна только владельцу (`TELEGRAM_CHAT_ID`).

### 8.2. Переключение (цель ≤ 5 мин)

1. Сторож фиксирует отказ (≈ 1–2 мин), пишет в Telegram (через xray из дома) и **ждёт
   подтверждения** (в автоматическом режиме — действует сразу).
2. Скрипт `promote.sh` на Pi:
   1. `docker service scale bridge_backend=1` на резервном Swarm (БД уже
      восстановлена ночным дампом — старт ≈ 30–60 с, миграции — секунды);
   2. включить в резервном стеке опрос Telegram и планировщики (они в коде
      backend, стартуют вместе с ним — поэтому backend и был остановлен);
   3. проверить `health`;
   4. переключить DNS (API провайдера DNS) на внешний IP дома, TTL 60 с;
   5. записать событие, отправить уведомление.
3. Пользователи видят сервис ≈ через 1–3 мин после смены DNS.

### 8.3. Возврат (failback) — осознанный, не автоматический

1. Основная площадка восстановлена и проверена.
2. Выбрать источник истины: **резерв, если на нём были записи** (почти всегда).
3. `pg_dump` с резерва → восстановление в Selectel → переключение DNS обратно →
   `backend=0` на резерве. Окно записи на время восстановления (read-only
   режим/страница обслуживания).
4. Если данные на основной площадке свежее резерва (редкий случай «ложного
   срабатывания») — перенос в обратную сторону вручную, решение за вами.

### 8.4. Борьба со split-brain

- Нельзя, чтобы одновременно работали **два** backend: дублируются планировщики
  Improve (`@Interval`), конфликтует Telegram long-polling (HTTP 409), двоятся
  уведомления. Поэтому у резерва backend остановлен, а DNS указывает ровно на
  одну площадку.
- Если Selectel «оживает» после переключения, **его backend нужно остановить**
  (сторож пытается через API Selectel; иначе — ваша процедура §8.3).
- Воркеров на обеих площадках разрешено держать одновременно: каждый
  опрашивает bridge по DNS-имени, то есть работает с активной площадкой.

## 10. Секреты и ключи

Без этих значений на резервной площадке система не заработает или не
расшифрует данные. GitHub Secrets **прочитать обратно нельзя**, поэтому нужна
независимая копия:

- `CREDENTIALS_ENC_KEY` — **критичный**: без него `ClaudeCredential.token`,
  `VpnConnection.panelApiToken`, `Secret.value`, `Context.content`,
  `Job.contextText/historyText` не расшифровываются;
- `JWT_SECRET`, `REFRESH_JWT_SECRET` — сессии переживают переключение только
  при тех же значениях;
- пароли и параметры БД, ключи S3, `YANDEX_ID/SECRET`, `GITHUB_OAUTH_*`,
  `BRIDGE_GITHUB_TOKEN`, `LOOP_GITHUB_TOKEN`, `TELEGRAM_*`, ключи worker;
- SSH-ключи деплоя, WireGuard-ключи, ключ `age` для бэкапов.

Хранение: файл секретов, зашифрованный **`age`/`sops`**, в двух местах — на
Pi (отдельный раздел) и **вне дома и вне облака** (носитель в сейфе/у близких;
бумажная копия `CREDENTIALS_ENC_KEY` и ключа `age`). Ключ шифрования бэкапов
**не** лежит рядом с бэкапами.

## 14. Риски

| Риск | Смягчение |
|---|---|
| Домашний канал/питание — единая точка отказа резерва | ИБП, LTE для исходящих, резерв не единственный (S3 + позже Яндекс) |
| Pi/NVMe выходят из строя (износ, троттлинг) | мониторинг SMART, запасной NVMe, Ansible — переустановка за минуты |
| Резерв отстал по версии | CI деплоит на обе площадки одним прогоном, алерт на дрейф SHA |
| Ложное срабатывание сторожа | два независимых наблюдателя, порог ≈ 80 с, ручное подтверждение на первом этапе |
| Потеря `CREDENTIALS_ENC_KEY` | независимая копия (§10) |
| Хранение «только последней копии» | «проверить, потом заменить»; параметр `KEEP` |
| Размер uploads > ёмкости Garage | приоритеты (§6.3), докупка NVMe |
| OAuth: блокировка пользователя собственными настройками | серверный инвариант «≥ 1 способ» + аварийный API-ключ |
| Selectel/Managed БД: ограничения экспорта | проверить `pg_dump` через private/floating IP на этапе 1 |
