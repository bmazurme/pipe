## Где harness сейчас

`harness/src/status.ts` (`pipe-status`) — read-only отчёт. Он читает 4 локальных JSON-файла (`.sync-state.json`, `.sync-agent-state.json`, `.gitlab-worker-state.json`, `subscription-state.json` из reports), сводит их по ключу `projectId:iid`, выводит статус на каждую задачу (`deriveStatus`), помечает зависшие задачи (`--stale-after`) и умеет `--json`, `--filter`, `--watch`. Ненулевой код выхода можно использовать как health-check.

Чего ему не хватает, чтобы быть помощником:

- **Он видит только одну машину и только локальные файлы, по умолчанию.** Задачи worker (`jobs` в Postgres), статус worker (heartbeat), посылки в storage и состояние issue в GitLab (открыта/закрыта, MR, пайплайн) все теперь видны под опциональным `--live` (1.1 — bridge, 1.2/1.3 — GitLab, независимо друг от друга) — просто не включено по умолчанию. Чат по-прежнему не видно совсем — это не в scope ни одного из пунктов 1.x.
- **Он ничего не делает.** Только показывает. Следующий шаг (pull, publish, повтор задачи) пользователь должен вспомнить и выполнить сам, в другом инструменте.
- **Он не сообщает сам.** `--watch` перепечатывает весь отчёт и не говорит, что изменилось; уведомлений нет, хотя в `sync/src/notify.ts` они уже реализованы.
- **У него нет памяти.** Есть только текущий снимок, а истории по задаче (когда ушла, сколько ехала, какая модель, сколько попыток) нет.

## Предлагаемый порядок

Весь раздел 1 («Видеть всё») теперь закрыт (1.1/1.2/1.3), как и фундамент
(раздел 6, целиком). Это ровно то, ради чего разделы были в таком порядке —
дальше идёт собственно «помощник», а не просто более полный отчёт:

1. **Фундамент:** 6.1 → 6.2 → 6.3 → **✅ Выполнено полностью.**
2. **Полнота картины:** 1.1 (bridge) → 1.2/1.3 (GitLab) → **✅ Выполнено
   полностью.** 1.2 опирался на технический документ 2.1 (общий GitLab-клиент)
   — сделан там первым, как и предполагалось, `harness/src/gitlabLive.ts`
   просто переиспользовал `@pipe/protocol/gitlabClient` вместо третьей
   реализации с нуля.
3. **4.1 (журнал событий) — ✅ Выполнено полностью**, и раньше 3.1, в
   обратном порядке от исходной формулировки — см. его собственную строку
   для почему. Diff/snapshot-движок (`harness/src/events.ts`) теперь уже
   существует и проверен; это меняет расклад для следующего пункта.
4. **Сразу следующее — самая ценная ещё не начатая пара:** этого документа
   собственный **2.1** («следующее действие для каждой задачи», P0 — не
   путать с техническим документом 2.1, который про общий HTTP-клиент и уже
   закрыт) + **3.1** (демон + уведомления о переходах, P0). Это то, что
   превращает `pipe-status` в помощника, а не просто отчёт — конкретная
