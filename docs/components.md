# Components in detail: bridge, worker, chat

Moved out of `CLAUDE.md` unchanged so that file stays short enough to read in one go. These are the long, fast-changing
per-feature descriptions; `CLAUDE.md` keeps only the summary and the rules that matter for every change. When you change
one of these modules, update this file, not `CLAUDE.md`.

## bridge (NestJS + React)
`apps/backend/src` is organized by feature module: `auth` (JWT access + refresh-token rotation + personal API keys + per-user sign-in methods in `auth_identities` — Yandex and GitHub, each switchable from the profile, the server always keeps at least one enabled; urgent and messages with buttons are never held); quiet hours and the morning digest are as before and win over the burst. (1) A plain question about the system — `detectIntent`: «что сломалось / что с системой / статус» or «объясни / почему упал запуск N» — gets a snapshot appended to the turn's `context` in `ChatTurnsController.claim` (works for Claude too, no tool loop; never for the router's internal chats, never for a non-owner; a snapshot that fails is skipped, not a failed turn): bridge health, `DriftService.view` (R1), workers online/not seen, Improve runs and Worker jobs failed in 24 h, runs waiting for answers (A6), the warn/error log grouped by event; or one run explained (`improve_runs` + `jobs` by the same number: status, error, gate retries, escalation, cost, end of the log). (2) `GET /chat/tools` + `POST /chat/tools/call` (`@MachineOnly @WorkerKeyAllowed`, owner only) serve the same facts as tools `system_status`, `explain_run`, `recent_runs` to gpt/deepseek/qwen turns; the worker relays the call with its own `brw_` key (`createBridgeToolset`/`toolsetForTurn`), so a worker added from the UI has tools now (before, `loop.ts` forced them off because its key could not reach the older ones). `WORKER_CHAT_TOOLS` defaults to `read`. Nothing writes: the only way a chat changes anything is still the `pipe-action` card the person presses (fix-pr / merge-pr), `create_job` stays `write`-mode and personal-key only. **Worker container hardening (S1(2), `worker/Dockerfile`, `docker-entrypoint.sh`, `worker/src/runAs.ts`, board agent v7):** the image no longer uses sudo (a setuid binary cannot work under `no-new-privileges`/`--cap-drop ALL`): the entrypoint, the only root process, starts the worker as `pipe-worker` (uid/gid pinned 100/101 so older volumes keep working) with only CAP_SETUID/CAP_SETGID as ambient capabilities + no-new-privs, and the worker starts job code through `setpriv --reuid=pipe-runner … --inh-caps=-all --ambient-caps=-all --no-new-privs` (`WORKER_RUN_AS_VIA=setpriv`; bare metal keeps `sudo`). Proven in a container run with `--cap-drop ALL --cap-add SETUID,SETGID,SETPCAP --security-opt no-new-privileges --read-only` + tmpfs: job code has no capability, cannot read `.worker-state`/the worker's environ, cannot switch to the worker or root, and writes only its job directory, its home and /tmp. The board agent (v7) carries over such flags when it recreates a worker and, with `WORKER_HARDEN=1` in the board's settings file (off by default, one board at a time), adds the whole set plus a `<container>-work` volume; anything else it adds or sees (other capabilities, seccomp/apparmor, other tmpfs, bind mounts) is still refused.

`apps/frontend/src` uses Gravity UI (`@gravity-ui/uikit` + `@gravity-ui/navigation` + `@gravity-ui/aikit` for the Chat page), Redux Toolkit + RTK Query, and a `base-query-with-reauth.ts` wrapper that transparently retries a request after a 401 by refreshing the access token (mutex-guarded so two simultaneous 401s can't race the refresh-token rotation and log each other out). Only the frontend depends on `@pipe/protocol` (for `dictionary`, `leakScan` and `encryption-browser`) — the backend has none, since both Purge's substitution and Storage's pre-upload leak scan happen client-side, before anything reaches the network.

`GET /api/v1/health` is readiness (DB reachable + no pending migrations), not just liveness — the plain `GET /` stays a trivial no-DB check on purpose (see `src/app.service.ts`); the Swarm healthcheck and deploy smoke test both target the former.

**Restore drill (R7).** A backup that was never restored is a hope, so `infra/backup/restore-drill.sh` restores the latest dump into a throwaway Postgres, checks the key tables hold rows, times it, and posts the result to `POST /api/v1/boards/agent/restore-drill` (a `boards`-scope key is enough; a *failed* drill is posted too). `boards/restore-drill.service.ts` keeps the last 24 runs in `restore_drills`; `boards/restore-drill.ts` (pure) turns them into a verdict (ok / warn after 30 days / bad after 35 days, on a failed run, on a key table that went empty, on a restored copy that was already stale) served at `GET /api/v1/dashboard/restore-drill` (Dashboard → Backups tile and the attention list). Telegram says it at once for a failed drill and once a day while the 35-day rule is broken; a drill that never ran shows only on the Dashboard.

## worker
A standalone, unprivileged process with no listening port — it only ever polls bridge (`GET`-then-`POST .../claim` for both Worker jobs and Chat turns, same loop, job claim always tried first each tick), never the reverse. Jobs run either the `claude` CLI (`--dangerously-skip-permissions`, sonnet/opus/haiku — genuinely arbitrary code execution against task content, hence the process isolation) or a minimal OpenAI-compatible tool-calling loop (gpt/deepseek/qwen, no shell tool). Chat turns are much simpler — one model call, no files, no tool loop — and share the exact same provider config as jobs for gpt/deepseek/qwen. Workers are added from the UI (Worker → Worker'ы), not configured with secrets: bridge creates a `workers` row and a 30-minute single-use code (`brn_…`); the process redeems it (`enrollCli.js`, or `WORKER_ENROLL_CODE`) for its own key (`brw_…`, stored hashed in bridge, kept by the worker in `WORKER_STATE_DIR` at 0600), accepted only on routes marked `@WorkerKeyAllowed()` (claim, heartbeat, the held job's parcel/status/logs/result, chat turns, `GET /workers/me/config`). Its settings (paused, models, poll interval, job timeout, proxy, chat on/off) are fetched before every poll; a 401 there means it was deleted/reconnected, so it erases its key and waits to be enrolled again. Claude tokens and gpt/deepseek/qwen API keys live encrypted in bridge (`claude_credentials`, `provider_credentials`) and arrive with the claimed job or chat turn (the worker's environment is only a fallback). A seventh model, `custom`, is any other OpenAI-compatible server (Yandex AI Studio, Gemini, Ollama, LM Studio, a gateway…): it is described entirely by a `provider_credentials` row with `provider: 'custom'` — address, model, `authScheme` (bearer / api-key / none), encrypted `extraHeaders`, `timeoutSec`, `supportsTools`, `route` (auto / vpn / direct, decided per request by `worker/src/routing.ts`: in `auto` a private address goes direct and a public one through the worker's VPN when it has one; `vpn` refuses to run without one), `allowedWorkerIds` — so a new service needs no enum value or migration. A custom job must name its key (`providerCredentialId`; there is no "first custom key"), only a worker of at least `MIN_CUSTOM_WORKER_VERSION` is given it (workers report their version on every settings fetch, `X-Worker-Version`), and only one in the key's `allowedWorkerIds`. Improve and Lab keep a run's model in their ordinary `model` column, and a custom one as `custom:<key id>` (`jobModelOf` in `improve/improve-shared.ts` turns it into the job's model + `providerCredentialId`, `requireImproveModel` accepts it; a Lab run on the Fusion executor needs a Claude model, since Fusion is driven from a shell); their pickers list every custom key as a model (`useModelOptions`). A run on an OpenAI-compatible model reports the tokens the server counted (`usage` of each completion, summed) to `POST /worker/jobs/usage` like a Claude run, with `costUsd` priced from the key's `priceInPerMTok`/`priceOutPerMTok` (null for a free local model); the usage page shows each custom key as its own model ("custom · Mac M2"). A chat can run on it too (`chats.model = 'custom'` + `chats.providerCredentialId`, the key being chosen in the composer): its turn is claimed under the same rule as a job (`claimCustomChatSql` — a managed worker of at least that version, in the key's `allowedWorkerIds`), the key's description arrives with the claimed turn, and a key with `stream` makes the worker send `stream: true` and report the answer as it grows (the same `POST /chat/turns/:id/progress` as a Claude turn; a round with bridge tools is not streamed, and a server that ignores `stream` is read as plain JSON). A custom chat takes no attachments (only Claude reads them). Which Claude token a sonnet/opus/haiku run (job or chat turn) uses: the one the job picked, else the one set in the worker's settings (`workers.claudeCredentialId`), else the account's first stored token — a worker added in the UI has no login of its own, so bridge always hands it one at claim. A token Anthropic refused is marked rejected: when a Claude job fails and its message matches `AUTH_FAILURE_PATTERN` (`worker.service.ts`: `Failed to authenticate`, `401`, `403` followed by `Request not allowed`, or `has disabled Claude subscription access`), bridge sets `authFailedAt`/`authFailedJobId` on the token that job used. The last fallback above (the account's first stored token) skips marked tokens while an unmarked one exists; a token named explicitly by the job or the worker's settings is still used. The mark is cleared by a later succeeded job on that token, or by replacing the token's value. Other wording is not matched — e.g. «This organization has been disabled» marks nothing, so such a token stays unmarked. A worker's own VPN is also a UI setting: a `vless://` Reality link (`workers.vpnLink`, encrypted, write-only — the owner's views only get `vpnHost`) that only that worker receives in its settings fetch (or, with `workers.vpnSource` `connection`/`active`, the link bridge builds from a connection of the VPN page — the chosen one or whichever is active there — through `VpnLinkResolver`: cached for a minute, kept at its last good value while the panel is down, and if the panel never answered the settings fetch fails so the worker keeps its last tunnel); the worker runs its own Xray client with it (`worker/src/vpn/`, the pinned `xray` binary is copied into the worker image) and routes Claude/AI traffic through that loopback HTTP proxy, so a node needs no separate vpn-client container — the Add-worker dialog hands out one `docker run` command (container and state volume named after the worker) and everything else (token, VPN, models, timeouts) is set in the UI. A job is for any free worker, or pinned (`targetWorkerId`) to one; a managed worker takes one job at a time, only its models, only unpinned or its own; a legacy worker (personal API key in `BRIDGE_API_KEY`) still works but never takes a pinned job. Claude runs use `--output-format stream-json`: besides the reply text, worker reads the CLI's `rate_limit_event` (plan windows: 5 h, week, …) and `result` (tokens, cost) and posts them best-effort to `POST /worker/jobs/usage` — bridge keeps the limits as a snapshot on the worker row and on the job's named Claude token (`claudeLimits` / `limits`, shown as bars on the Worker page with "data as of") and tokens/cost on the job (`usage`). The numbers can be refreshed without a job: "Обновить лимиты" on a worker's card (`POST /workers/:id/refresh-limits` stamps `workers.limitsRefreshRequestedAt`) or, if chosen in its settings, every `limitsRefreshMin` minutes — the worker sees it in its settings fetch (which then also carries the token to probe with, only while a probe is due), runs one tiny CLI call (`worker/src/limitsProbe.ts`: bare system prompt, no tools, ~4k tokens; haiku first, then sonnet if a token cannot use it — the one that worked is remembered) and reports it with `probe: true`, so the limits land on the worker and on the token its jobs use. Each report is also checked by `LimitAlertsService`: when a plan window of a token (or of a worker, when the token is unknown) crosses 80 % / 95 % / is rejected, the owner gets one Telegram message per level and window (through NotifyService, so quiet hours apply; what was announced is kept in `limit_alert_states`, a window that rolls over starts again; `LIMIT_ALERTS=off` silences it). The CLI reports limits only while it runs, so they are never live; gpt/deepseek/qwen report none. A worker can also run on a Mac next to Autodesk Fusion 360 (`worker/fusion-addin/`: the `PipeFusion` add-in runs inside Fusion and serves 127.0.0.1 with a token written to `~/.pipe-fusion/config.json`; `worker/src/fusion/` has the client, the `fusionctl` CLI the model drives it with from its shell — run a script in Fusion, screenshot, export STEP/STL/F3D — and the prompt that explains it). That worker has the `fusion` capability set in its settings, and a job with `requiredCapability: 'fusion'` (Lab's "Fusion 360 на Mac" executor) is given only to it; before the model starts the worker checks the add-in answers, and the job needs a Claude model (a shell). The add-in's own logic is tested with Python's `unittest` (`python3 -m unittest discover -s worker/fusion-addin/tests`, also run in CI). The poll loop is `worker/src/loop.ts` (injected dependencies, unit-tested). Every outbound `fetch` (to bridge and to AI providers) carries an `AbortSignal.timeout`; job logs are batched (flushed every ~1.5s, at most one send in flight — text logged meanwhile waits for the next one, capped at 2M chars with a "dropped" marker past that, and the end-of-job drain gives up after 30 s) rather than one `POST` per output chunk.

## chat
Independent of the parcel/Worker-job pipeline end to end — no files, no parcel, just a plain conversation with Claude/GPT/DeepSeek/Qwen through worker. `bridge/apps/backend/src/chat` persists `Chat`/`ChatMessage` rows (a pending assistant message is created in the same request as the user's message, so the frontend has something to poll immediately); worker's `chatProviders.ts`/`chatRunners/*` execute a turn and report back. No streaming — bridge has no websocket/SSE infrastructure anywhere, so, like everything else, the frontend polls. What it polls shows the reply growing, though: a Claude turn runs the CLI with `--include-partial-messages`, the worker reports the text so far (throttled, `POST /chat/turns/:id/progress` → `chat_messages.progress`, cleared when the turn ends), and the page renders it in the pending bubble — or, before the first words, "Ждём свободный worker… / Модель работает… N с" ticking each second. gpt/deepseek/qwen show only that waiting stage (their runner does not stream). Claude chats (sonnet/opus/haiku only) can carry attachments — images, pdf, text and source files (`chat_attachments`, bytes in the same `FileStore` as Storage under `chat/` keys — local volume or the S3 bucket, per `STORAGE_DRIVER` — kept apart from Storage's mailbox semantics: never deleted on download): uploaded first, linked to the message when it is sent, listed in the claimed turn's history, fetched one by one by the worker into the turn's scratch directory where Claude Code reads them. A whole chat can be saved as a Context from the chat page's menu. The outcome of a finished Worker job can be attached to a chat from the same menu (`POST /chat/chats/:id/run-results` → `ChatService.attachRunResult`): it appends `describeRun`'s text (status, error, end of the log — the same one Worker's "earlier runs" history uses) to the chat's context snapshot, within the Context length limit, once per run. A chat turn still has no repository or git; instead the model can *propose* a change to an open pull request by ending its reply with a ```pipe-action block (`worker/src/chatRunners/chatActions.ts` tells it how). The chat page strips the block from the text and shows it as a confirmation card (`pages/ChatPage/PrFixCard.tsx`); only "Запустить" calls `POST /improve/pr-fix` → `ImproveService.startPrFix`, which hands the PR's branch plus the request to a worker as a `repair` run with `trigger: 'chat'` (a new commit on that branch, same protected-path filter as every Improve run; chat runs do not count against CI's two automatic repairs).
