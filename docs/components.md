# Components in detail: bridge, worker, chat

Moved out of `CLAUDE.md` unchanged so that file stays short enough to read in one go. These are the long, fast-changing
per-feature descriptions; `CLAUDE.md` keeps only the summary and the rules that matter for every change. When you change
one of these modules, update this file, not `CLAUDE.md`.

## bridge (NestJS + React)
`apps/backend/src` is organized by feature module: `auth` (JWT access + refresh-token rotation + personal API keys + per-user sign-in methods in `auth_identities` — Yandex and GitHub, each switchable from the profile, the server always keeps at least one enabled; the Yandex/GitHub strategies and the "connect another method" flow live in `oauth`), `storage` (the file relay sync/reports build on — files go through a `FileStore` (`storage/file-store/`: `local` volume by default, or `STORAGE_DRIVER=s3` for a bucket such as Garage; chat attachments use the same store under `chat/` keys, so code never builds a disk path itself, it calls `store.*`/`StorageService.download`) — download-then-delete, a deliberate "single-recipient mailbox" semantics; see `sync/README.md` for why that shape matters to the push/pull protocol), `purge` (the per-account dictionary, also consumed by bridge's own frontend), `secrets` (a personal vault of arbitrary name/value pairs the user manages from the frontend — unrelated to Worker's own machine credentials below, never read by worker or any other product, only revealed back to the owning user through this module's own endpoint), `time` (days-off/report import-export for `reports` and ntlstl.time — machine callers authenticate with a personal API key like every other integration), `users`, `worker` (Worker jobs, named Claude credentials, and the heartbeat bridge uses to show worker up/down on the Worker page), `vpn` (named VPN panel connections worker's outbound traffic can route through, plus server-provisioning; a status check that fails pages the owner once on Telegram — not per poll — and once more when it recovers, through the same `NotifyService` as `LimitAlertsService`; `VPN_ALERTS=off` silences it), `chat` (a plain conversational module, unrelated to the parcel/job flow — see its own section below). `improve` (the self-improvement runs on bridge itself — an analysis proposes one item per chosen direction, and "Новые фичи" (`features`) is an opt-in direction that proposes a new capability grounded in the project's own context (CLAUDE.md, READMEs, existing pages), off by default so existing schedules do not change; "Рефакторинг" (`refactoring`) is the second opt-in direction — one small behavior-preserving code-level refactor (duplication, an overlong function, dead code, a stray `any`), distinct from `architecture`'s module boundaries: issue → worker → branch + PR, repository analyses, nightly schedules; an open PR it made that goes red in CI is handed back to a worker on its own branch — `improve-ci.service.ts`, at most twice per PR and once per head commit, switchable per account — and a PR that cannot be opened leaves no branch behind). `lab` (Improve for the owner's OWN GitHub repositories: a `LabProject` is `owner/name` + a personal token — encrypted at rest like the other credentials, never returned, only `tokenHint` — verified on connect and by "Проверить" with a read and a harmless write probe; a `LabRun` snapshots the project's base branch, hands the free-text task to a worker and opens a branch `lab/run-<id>-…` plus a pull request with the result, never merging (the Runs tab's "Проверить PR" — owner-triggered, no polling — asks GitHub about up to 20 open ones and moves a merged/closed PR's run to `pr_merged`/`pr_closed`, which ends "Доработать" for it); `LabSchedule` is a nightly run of a text task on one project, and a run/schedule picks where it runs from a list (`executor`: `any` worker, or `fusion` — only a worker with the `fusion` capability, i.e. one set up on a Mac next to Fusion 360; a job carries it as `requiredCapability`, `WorkerService.claim` hands such a job only to a worker whose `workers.capabilities` has it, and a run for which no enabled such worker exists is refused up front), same compare-and-set slot claim as Improve's; changes under `.github/workflows/` and `.git/` are dropped; it reuses Improve's parcel helpers and the loop's `GithubApiService` through a per-project config adapter in `lab/lab-github.ts`, and does not touch `src/loop`). `boards` (what each board's agent reports about its installed scripts against `main`, and the owner's decision to update them: the agent — `infra/boardagent`, authenticating with the owner's personal API key, owner only — posts `board_reports`; an outdated board is announced once on Telegram with a button `su:<host>:<sha7>` handled in `TelegramCommandsService`, or updated from the page «Платы»; either records a `script_updates` decision for the commit of the report, which the agent picks up, checks (the commit must be on `main`) and applies only to scripts it already knows; the agent can update itself too (its script and manifest only), but only after the new version passes its own `selftest`, with the old pair kept and a `rollback.sh` unit putting it back if the new one crashes on its first run; a decision nobody collects expires in an hour). `questions` (open questions per task: after a run the worker reads a fenced ```pipe-questions block from the model's output — the prompt asks for it, `worker/src/taskQuestions.ts` — and reports it, best-effort, to `POST /worker/jobs/:id/questions`; bridge stores one `task_questions` row per question and the page «Questions» shows a card per task (`taskKey`), tagged with the project number — the part of `projectId:iid` before the colon — with a checkbox per question; a card with every question ticked is archived, and a new open question on the task brings it back; a question already open on the task is not added twice). `context` (named, reusable background text a user attaches to a Worker job at launch — none by default; the job keeps its own snapshot of it; a job can also be launched with the outcomes of earlier runs of the same task mixed in (assembled by bridge from those jobs' errors and log tails, snapshotted the same way) — either, both or neither; only the claiming worker ever receives the text, which it puts in front of the task prompt). An Improve schedule (nightly analysis or issue runs) can carry a Context too (`improve_schedules.contextId`, FK ON DELETE SET NULL): every run it starts hands that context to its worker job like a hand-launched one. Two guards matter: `JwtGuard` (browser session — `purge`, `secrets` and `vpn`'s provisioning routes all use this one, never the machine-auth guard, since none of the three is ever called by sync/reports/worker) and `JwtOrApiKeyGuard` (accepts either a JWT or a personal API key — what lets sync/reports/worker authenticate as a machine instead of replaying a browser cookie). `ClaudeCredential.token`, `VpnConnection.panelApiToken` and `Secret.value` are encrypted at rest (AES-256-GCM via `src/crypto/encrypted-column.transformer.ts`, keyed by `CREDENTIALS_ENC_KEY`) — a DB dump no longer hands over a usable secret. A global `ThrottlerGuard` (`@nestjs/throttler`) rate-limits every route; `AuthController`/`OauthController` carry a much stricter override of their own, since those are the genuinely brute-forceable, never-polled routes.

`apps/frontend/src` uses Gravity UI (`@gravity-ui/uikit` + `@gravity-ui/navigation` + `@gravity-ui/aikit` for the Chat page), Redux Toolkit + RTK Query, and a `base-query-with-reauth.ts` wrapper that transparently retries a request after a 401 by refreshing the access token (mutex-guarded so two simultaneous 401s can't race the refresh-token rotation and log each other out). Only the frontend depends on `@pipe/protocol` (for `dictionary`, `leakScan` and `encryption-browser`) — the backend has none, since both Purge's substitution and Storage's pre-upload leak scan happen client-side, before anything reaches the network.

`GET /api/v1/health` is readiness (DB reachable + no pending migrations), not just liveness — the plain `GET /` stays a trivial no-DB check on purpose (see `src/app.service.ts`); the Swarm healthcheck and deploy smoke test both target the former.

## worker
A standalone, unprivileged process with no listening port — it only ever polls bridge (`GET`-then-`POST .../claim` for both Worker jobs and Chat turns, same loop, job claim always tried first each tick), never the reverse. Jobs run either the `claude` CLI (`--dangerously-skip-permissions`, sonnet/opus/haiku — genuinely arbitrary code execution against task content, hence the process isolation) or a minimal OpenAI-compatible tool-calling loop (gpt/deepseek/qwen, no shell tool). Chat turns are much simpler — one model call, no files, no tool loop — and share the exact same provider config as jobs for gpt/deepseek/qwen. Workers are added from the UI (Worker → Worker'ы), not configured with secrets: bridge creates a `workers` row and a 30-minute single-use code (`brn_…`); the process redeems it (`enrollCli.js`, or `WORKER_ENROLL_CODE`) for its own key (`brw_…`, stored hashed in bridge, kept by the worker in `WORKER_STATE_DIR` at 0600), accepted only on routes marked `@WorkerKeyAllowed()` (claim, heartbeat, the held job's parcel/status/logs/result, chat turns, `GET /workers/me/config`). Its settings (paused, models, poll interval, job timeout, proxy, chat on/off) are fetched before every poll; a 401 there means it was deleted/reconnected, so it erases its key and waits to be enrolled again. Claude tokens and gpt/deepseek/qwen API keys live encrypted in bridge (`claude_credentials`, `provider_credentials`) and arrive with the claimed job or chat turn (the worker's environment is only a fallback). Which Claude token a sonnet/opus/haiku run (job or chat turn) uses: the one the job picked, else the one set in the worker's settings (`workers.claudeCredentialId`), else the account's first stored token — a worker added in the UI has no login of its own, so bridge always hands it one at claim. A worker's own VPN is also a UI setting: a `vless://` Reality link (`workers.vpnLink`, encrypted, write-only — the owner's views only get `vpnHost`) that only that worker receives in its settings fetch; the worker runs its own Xray client with it (`worker/src/vpn/`, the pinned `xray` binary is copied into the worker image) and routes Claude/AI traffic through that loopback HTTP proxy, so a node needs no separate vpn-client container — the Add-worker dialog hands out one `docker run` command (container and state volume named after the worker) and everything else (token, VPN, models, timeouts) is set in the UI. A job is for any free worker, or pinned (`targetWorkerId`) to one; a managed worker takes one job at a time, only its models, only unpinned or its own; a legacy worker (personal API key in `BRIDGE_API_KEY`) still works but never takes a pinned job. Claude runs use `--output-format stream-json`: besides the reply text, worker reads the CLI's `rate_limit_event` (plan windows: 5 h, week, …) and `result` (tokens, cost) and posts them best-effort to `POST /worker/jobs/usage` — bridge keeps the limits as a snapshot on the worker row and on the job's named Claude token (`claudeLimits` / `limits`, shown as bars on the Worker page with "data as of") and tokens/cost on the job (`usage`). The numbers can be refreshed without a job: "Обновить лимиты" on a worker's card (`POST /workers/:id/refresh-limits` stamps `workers.limitsRefreshRequestedAt`) or, if chosen in its settings, every `limitsRefreshMin` minutes — the worker sees it in its settings fetch (which then also carries the token to probe with, only while a probe is due), runs one tiny CLI call (`worker/src/limitsProbe.ts`: bare system prompt, no tools, ~4k tokens; haiku first, then sonnet if a token cannot use it — the one that worked is remembered) and reports it with `probe: true`, so the limits land on the worker and on the token its jobs use. Each report is also checked by `LimitAlertsService`: when a plan window of a token (or of a worker, when the token is unknown) crosses 80 % / 95 % / is rejected, the owner gets one Telegram message per level and window (through NotifyService, so quiet hours apply; what was announced is kept in `limit_alert_states`, a window that rolls over starts again; `LIMIT_ALERTS=off` silences it). The CLI reports limits only while it runs, so they are never live; gpt/deepseek/qwen report none. A worker can also run on a Mac next to Autodesk Fusion 360 (`worker/fusion-addin/`: the `PipeFusion` add-in runs inside Fusion and serves 127.0.0.1 with a token written to `~/.pipe-fusion/config.json`; `worker/src/fusion/` has the client, the `fusionctl` CLI the model drives it with from its shell — run a script in Fusion, screenshot, export STEP/STL/F3D — and the prompt that explains it). That worker has the `fusion` capability set in its settings, and a job with `requiredCapability: 'fusion'` (Lab's "Fusion 360 на Mac" executor) is given only to it; before the model starts the worker checks the add-in answers, and the job needs a Claude model (a shell). The add-in's own logic is tested with Python's `unittest` (`python3 -m unittest discover -s worker/fusion-addin/tests`, also run in CI). The poll loop is `worker/src/loop.ts` (injected dependencies, unit-tested). Every outbound `fetch` (to bridge and to AI providers) carries an `AbortSignal.timeout`; job logs are batched (flushed every ~1.5s, at most one send in flight — text logged meanwhile waits for the next one, capped at 2M chars with a "dropped" marker past that, and the end-of-job drain gives up after 30 s) rather than one `POST` per output chunk.

## chat
Independent of the parcel/Worker-job pipeline end to end — no files, no parcel, just a plain conversation with Claude/GPT/DeepSeek/Qwen through worker. `bridge/apps/backend/src/chat` persists `Chat`/`ChatMessage` rows (a pending assistant message is created in the same request as the user's message, so the frontend has something to poll immediately); worker's `chatProviders.ts`/`chatRunners/*` execute a turn and report back. No streaming — bridge has no websocket/SSE infrastructure anywhere, so, like everything else, the frontend polls. What it polls shows the reply growing, though: a Claude turn runs the CLI with `--include-partial-messages`, the worker reports the text so far (throttled, `POST /chat/turns/:id/progress` → `chat_messages.progress`, cleared when the turn ends), and the page renders it in the pending bubble — or, before the first words, "Ждём свободный worker… / Модель работает… N с" ticking each second. gpt/deepseek/qwen show only that waiting stage (their runner does not stream). Claude chats (sonnet/opus/haiku only) can carry attachments — images, pdf, text and source files (`chat_attachments`, bytes in the same `FileStore` as Storage under `chat/` keys — local volume or the S3 bucket, per `STORAGE_DRIVER` — kept apart from Storage's mailbox semantics: never deleted on download): uploaded first, linked to the message when it is sent, listed in the claimed turn's history, fetched one by one by the worker into the turn's scratch directory where Claude Code reads them. A whole chat can be saved as a Context from the chat page's menu. The outcome of a finished Worker job can be attached to a chat from the same menu (`POST /chat/chats/:id/run-results` → `ChatService.attachRunResult`): it appends `describeRun`'s text (status, error, end of the log — the same one Worker's "earlier runs" history uses) to the chat's context snapshot, within the Context length limit, once per run. A chat turn still has no repository or git; instead the model can *propose* a change to an open pull request by ending its reply with a ```pipe-action block (`worker/src/chatRunners/chatActions.ts` tells it how). The chat page strips the block from the text and shows it as a confirmation card (`pages/chat/PrFixCard.tsx`); only "Запустить" calls `POST /improve/pr-fix` → `ImproveService.startPrFix`, which hands the PR's branch plus the request to a worker as a `repair` run with `trigger: 'chat'` (a new commit on that branch, same protected-path filter as every Improve run; chat runs do not count against CI's two automatic repairs).
