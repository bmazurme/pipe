## Где harness сейчас

`harness/src/status.ts` (`pipe-status`) — read-only отчёт. Он читает 4 локальных JSON-файла (`.sync-state.json`, `.sync-agent-state.json`, `.gitlab-worker-state.json`, `subscription-state.json` из reports), сводит их по ключу `projectId:iid`, выводит статус на каждую задачу (`deriveStatus`), помечает зависшие задачи (`--stale-after`) и умеет `--json`, `--filter`, `--watch`. Ненулевой код выхода можно использовать как health-check.

Чего ему не хватает, чтобы быть помощником:

- **Он видит только одну машину и только локальные файлы.** Задачи worker (`jobs` в Postgres), статус worker (heartbeat), чат, посылки, лежащие в storage, и состояние issue в GitLab ему не видны. Поэтому статус «likely ready to pull» — это догадка, а не проверка.
- **Он ничего не делает.** Только показывает. Следующий шаг (pull, publish, повтор задачи) пользователь должен вспомнить и выполнить сам, в другом инструменте.
- **Он не сообщает сам.** `--watch` перепечатывает весь отчёт и не говорит, что изменилось; уведомлений нет, хотя в `sync/src/notify.ts` они уже реализованы.
- **У него нет памяти.** Есть только текущий снимок, а истории по задаче (когда ушла, сколько ехала, какая модель, сколько попыток) нет.

| 1.1 | P0 | **Живая проверка bridge.** Заменить «likely ready to pull» на факт: есть ли результат в storage, в каком статусе задача worker, жив ли worker. | Опциональный `--live` (или настройка): через API-ключ bridge (тот же механизм, что у sync/worker) вызывать `GET /storage` и `GET /worker/jobs`, а также новый `GET /worker/status` (heartbeat уже реализован в `worker-heartbeat.service.ts`). Без сети — текущий оффлайн-режим как fallback. |

## 2. Подсказывать и действовать

| # | Пр. | Улучшение | Как |
|---|---|---|---|
| 2.1 | P0 | **Следующее действие для каждой задачи.** Не только «pulled — ready to publish», но и конкретная команда. | Добавить в `DerivedStatus` поле `nextAction: { label, command? }`, например `sync-cli pull-issue foo 173 628` или «открыть reports → Subscription → Publish». | 2.2 | P1 | **`pipe next`** — одна самая важная задача прямо сейчас и что с ней сделать. | Скоринг: зависла > есть готовый результат > новая назначенная > в работе. Учитывать due date / приоритетные метки из GitLab (после 1.2). |
| 2.3 | P1 | **Выполнение действий** из harness: `pipe pull 173:628`, `pipe retry 173:628`, `pipe publish 173:628`. | Тонкая обёртка над уже существующими командами sync и HTTP-эндпоинтами reports/bridge. Любое действие с записью требует подтверждения (`--yes` для скриптов); `--dry-run` показывает, что было бы сделано. Auto-merge — никогда (это сознательное правило проекта). |
| 2.4 | P2 | **Интерактивный TUI** (`pipe` без аргументов): список задач, стрелки, Enter — действие из 2.1. | `ink` или `@clack/prompts`. Отчёт `formatReportText` остаётся для пайпов и CI. |

## 3. Сообщать самому

| 3.3 | P1 | **Каналы доставки** помимо OS-уведомлений — когда пользователь не за этой машиной. | Telegram-бот или web-push через bridge (уже есть авторизация и фронтенд). Достаточно одного канала, через интерфейс `Notifier`. |

## 6. Внутреннее качество harness (нужно для всего выше)

| # | Пр. | Улучшение | Как |
|---|---|---|---|
| 6.1 | P0 | **Типы state-файлов скопированы вручную** («Mirrors sync/src/types.ts… exactly»). Если sync/reports изменят формат, harness будет молча показывать неверные данные. | Вынести схемы state-файлов в `@pipe/protocol/state` (zod) — их используют и писатели (sync/reports), и читатель (harness). | 6.2 | P1 | **Один файл на 455 строк** смешивает чтение, логику статуса, форматирование и разбор CLI. | Разделить на `sources/` (интерфейс `StateSource` → `{ key, signals }[]`: localSync, localReports, bridgeLive, gitlab), `status.ts` (derive/next action), `render/` (text, json, brief), `cli.ts`. Новый источник — новый файл, а не правка `collectReportData`. |

| 6.5 | P2 | Название `pipe-status` уже уже, чем роль. | Переименовать бинарник в `pipe` с подкомандами (`status`, `next`, `brief`, `log`, `pull`…); `pipe-status` оставить алиасом. |

## Предлагаемый порядок

1. **Фундамент:** 6.1 → 6.2 → 6.3 (без них каждое следующее улучшение будет дороже).
2. **Сразу полезно:** 2.1 (следующее действие) + 1.1 (живая проверка bridge) — главное отличие «помощника» от отчёта.
3. **Помощник, который сам сообщает:** 3.1 (демон + уведомления о переходах) + 4.1 (журнал событий — бесплатно приходит вместе с демоном).
4. **Расширение:** 1.2/1.3 (GitLab), 3.2 (утренняя сводка), 5.1 (MCP), 4.2 (время в reports).
